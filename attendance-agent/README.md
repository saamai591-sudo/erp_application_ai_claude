# عامل تردد (Attendance Agent)

برنامه‌ی کوچکی که روی یک رایانه‌ی ویندوزی کنار دیتابیس سیستم کارت‌ساعت اجرا می‌شود، ثبت‌های ورود/خروج را **فقط‌خواندنی** از آن می‌خواند و با API به ERP می‌فرستد.
نگاشت «شناسه‌ی کاربر در دستگاه ← کارمند» در خود ERP انجام می‌شود (فرم «نگاشت شناسه‌ی دستگاه»)؛ این برنامه فقط شناسه‌ی خام را می‌فرستد.

## نصب با نصب‌کننده‌ی ویندوز (روش پیشنهادی)
`ERP-Attendance-Agent-Setup-<نسخه>.exe` را روی رایانه‌ی کنار دیتابیس کارت‌ساعت اجرا کنید (تأیید UAC لازم است؛ ویندوز ۱۰ / سرور ۲۰۱۶ به بالا؛ نصب Node.js لازم نیست). در پایان «صفحه‌ی تنظیم» در مرورگر باز می‌شود: آدرس ERP و توکن، مشخصات دیتابیس و جدول را بدهید، «آزمایش اتصال‌ها» و «پیش‌نمایش» را بزنید، «ذخیره» و سپس «نصب و شروع اجرای خودکار». بعداً از منوی Start › ERP Attendance Agent می‌توان دوباره تنظیم کرد، لاگ را دید یا یک دور دستی فرستاد. تنظیمات و لاگ در `C:ProgramDataERP Attendance Agent` می‌مانند.
ساخت نصب‌کننده (روی رایانه‌ی توسعه): `npm install` و `npm run build-installer` ← `dist/ERP-Attendance-Agent-Setup-<نسخه>.exe`.

**آدرس ERP:** در تنظیمات همان آدرسی را بنویسید که ERP با آن در مرورگر باز می‌شود (مثلاً `http://192.168.1.10:5174`)؛ عامل خودش آدرس API را پیدا می‌کند (به ترتیب: همان آدرس، `apiUrl` داخل `config.js` برنامه، `<آدرس>/api`، `hostname:4000/api`؛ هر کدام با `GET /health` امتحان می‌شود). اگر آدرس API را بدهید (مثلاً `http://192.168.1.10:4000/api`) همان به کار می‌رود.

**پنل «وضعیت و رکوردها»:** نصب‌کننده یک برنامه‌ی `ERP-Attendance-Agent.exe` می‌گذارد (میان‌بر روی دسکتاپ و منوی Start؛ UAC می‌خواهد). با اجرایش، بدون پنجره‌ی cmd، صفحه‌ای در مرورگر باز می‌شود با دو زبانه: **وضعیت و رکوردها** (خلاصه‌ی سرویس/آخرین ارسال/تعداد‌ها؛ فهرست ارسال‌ها به ERP با تعداد جدید/تکراری/پذیرفته/در انتظار نگاشت/ردشده؛ رکوردهای خوانده‌شده از دستگاه با جست‌وجوی شناسه‌ی کارت یا تاریخ و فیلتر وضعیت «ارسال شد / قابل تبدیل نبود»؛ خطاها و هشدارها؛ فایل لاگ) و **تنظیمات**. داده‌ی این زبانه از ژورنال محلی `agent-journal.db` (SQLite داخلی Node 22.5+، کنار فایل تنظیمات) می‌آید که خود عامل در هر ارسال می‌نویسد؛ ردیف‌ها و ارسال‌ها ۱۸۰ روز و خطاها ۹۰ روز نگه داشته می‌شوند. وضعیت پذیرش نهایی هر ردیف (پذیرفته/در انتظار نگاشت/ردشده با دلیل) در فرم «ثبت‌های دریافتی از دستگاه» ERP است.

## نصب دستی (توسعه)
## پیش‌نیاز
- Node.js 18 یا بالاتر روی همان رایانه.
- در ERP: فرم **تنظیمات › اتصال دستگاه حضور و غیاب** ← یک اتصال بسازید و **توکن** را (فقط یک بار نمایش داده می‌شود) نگه دارید.
- از شرکت کارت‌ساعت: نوع و آدرس دیتابیس، یک **کاربر فقط‌خواندنی**، نام جدول ورود/خروج و ستون‌ها (شناسه‌ی کاربر، تاریخ، ساعت یا تاریخ‌وساعت، و ستونی که ثبت تازه را از قدیمی جدا می‌کند: شناسه‌ی افزایشی یا زمان ثبت).

## راه‌اندازی
```powershell
cd attendance-agent
npm install
npm run setup          # پرسش‌وپاسخ؛ رمزها با DPAPI ویندوز محافظت می‌شوند
npm run test-connection   # اتصال به ERP و دیتابیس
npm run preview        # چند ردیف را خام و تبدیل‌شده نشان می‌دهد (چیزی ارسال نمی‌شود)
npm run once           # یک دور خواندن و ارسال
```
وقتی «preview» تاریخ و ساعت را درست نشان داد، برای اجرای دائمی (با روشن‌شدن رایانه، بدون ورود کاربر) از PowerShell با دسترسی Administrator:
```powershell
.\scripts\install-task.ps1
```
لاگ در `agent.log` کنار برنامه است. حذف: `.\scripts\uninstall-task.ps1`.

به‌جای «setup» می‌توان `agent.config.example.json` را به `agent.config.json` کپی و ویرایش کرد؛ رمز متن‌ساده در اولین اجرا خودکار رمز می‌شود.

## تنظیمات مهم (`agent.config.json`)
| کلید | توضیح |
|---|---|
| `db.type` | `mssql` (نمونه‌ی نام‌دار: `host: "SERVER\\INSTANCE"`)، `mysql` یا `postgres` |
| `source.table` | جدول ورود و خروج (مثلاً `dbo.Traffic`) |
| `source.columns` | `userId` الزامی؛ یا `dateTime` (یک ستون) یا هر دو `date` و `time`؛ `cursor` اختیاری (اگر نیامد، `cursorType` خودکار `auto` می‌شود)؛ `device` اختیاری |
| `source.dateFormat` | `gregorian` یا `jalali` (تاریخ متنی شمسی مثل `1405/08/20` یا `14050820`) |
| `source.cursorType` | `number` (شناسه‌ی افزایشی؛ شرط `>`)، `datetime` (زمان ثبت؛ شرط `>=` با هم‌پوشانی `overlapMinutes`) یا **`auto`** (بدون ستون پیگیری: با خودِ ستون‌های تاریخ و ساعت تردد، مرتب‌شده بر تاریخ و ساعت؛ شرط «تاریخ بزرگ‌تر، یا تاریخ برابر و ساعت بزرگ‌تر/مساوی»؛ ردیف‌های هم‌زمانِ آخر هر دور دوباره خوانده می‌شوند و ERP تکراری را نادیده می‌گیرد؛ ردیفی که با تاریخ قدیمی‌تر از آخرین مقدار و با تأخیر وارد جدول شود دیده نمی‌شود — در آن حالت ستون شناسه‌ی افزایشی بهتر است) |
| `source.initialCursor` | نقطه‌ی شروع اولین اجرا: `0` برای همه‌ی تاریخچه، یا برای زمانی مثلاً `"2026-11-01 00:00:00"`؛ در حالت `auto` تاریخ (و ساعت) با همان قالب دیتابیس، مثلاً `"2026-11-01"` یا `"1405/08/10 08:00"`، و خالی = همه‌ی تاریخچه |
| `source.startDate` | **تاریخ شروع خواندن** (اختیاری): فقط ثبت‌هایی که تاریخشان از این روز به بعد است خوانده می‌شود؛ شمسی (`1405/01/01`) یا میلادی (`2026-03-21`) با هر قالب ارقام. با هر نوع ستون پیگیری کار می‌کند. عامل آن را با قالب ستون تاریخ همان دیتابیس (شمسی/میلادی، جداکننده، ارقام) از روی یک ردیف نمونه می‌نویسد و شرط «ستون تاریخ >= شروع» را به SELECT اضافه می‌کند |
| `source.where` | شرط اضافه‌ی اختیاری (مثلاً `Deleted = 0`)؛ `;` و `--` مجاز نیست |
| `sync.intervalSeconds` / `batchSize` | فاصله‌ی دورها (۳۰۰) و اندازه‌ی هر خواندن (۲۰۰۰) |

ساعت‌ها قالب‌های `HH:mm`، `HH:mm:ss`، `HHmm` را می‌پذیرند؛ ارقام فارسی هم مجازند. ساعت همان ساعت دیواری دیتابیس است (ثانیه حذف می‌شود).

## نحوه‌ی کار و ایمنی
- **فقط SELECT**: تنها یک SELECT پارامتری ساخته می‌شود و نام‌ها با الگوی امن بررسی می‌شوند؛ با این حال حتماً از یک **کاربر فقط‌خواندنی** استفاده کنید.
- **ارسال مطمئن**: نقطه‌ی پیشرفت (`agent.state.json`) فقط پس از پذیرش سرور جلو می‌رود. قطع اینترنت یا خطای سرور ⇒ دور بعد از همان‌جا دوباره می‌فرستد؛ ارسال تکراری در ERP بی‌اثر است.
- **ردیف نامعتبر** (تاریخ/ساعت غیرقابل‌تبدیل) رد و در لاگ نوشته می‌شود و بقیه ادامه می‌یابند.
- ثبت‌هایی که شناسه‌شان نگاشت نشده یا ماهشان قفل است در ERP (فرم «ثبت‌های دریافتی از دستگاه») می‌مانند و با «پردازش مجدد» دوباره امتحان می‌شوند.
- رمزها با DPAPI سطح رایانه رمز می‌شوند (فایل کپی‌شده روی رایانه‌ی دیگر قابل‌خواندن نیست)؛ در لاگ هرگز رمز یا توکن نوشته نمی‌شود.

## آزمون
`npm run selftest` (بدون شبکه): تبدیل تاریخ شمسی/ساعت و ساخت SELECT را می‌آزماید.
