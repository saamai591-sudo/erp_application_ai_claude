# مستند پیاده‌سازی قابلیت «ویرایش مجدد» اعلامیه پرداخت

## 1. هدف

در سیستم دریافت و پرداخت، یک «اعلامیه پرداخت» می‌تواند شامل چند ابزار پرداخت باشد.

هر ابزار پرداخت نیز می‌تواند به یک یا چند «موضوع پرداخت» مرتبط باشد.

پس از تأیید اعلامیه پرداخت، ممکن است بعضی از ابزارهای پرداخت دارای گردش شده باشند و بعضی دیگر هنوز هیچ گردش نداشته باشند.

نیاز سیستم این است که:

* ابزارهای پرداخت دارای گردش تحت هیچ شرایطی قابل تغییر نباشند.
* ابزارهای پرداخت فاقد گردش امکان اصلاح داشته باشند.
* موضوعات پرداخت مرتبط با ابزارهای قابل اصلاح نیز همزمان قابل اصلاح باشند.
* در صورت تغییر مبلغ ابزار پرداخت، امکان اصلاح مبالغ موضوعات پرداخت مرتبط با آن وجود داشته باشد.
* امکان اضافه کردن موضوع پرداخت جدید برای ابزار پرداخت فاقد گردش وجود داشته باشد.
* ابزارهای دارای گردش و موضوعات پرداخت وابسته به آنها بدون تغییر باقی بمانند.
* این قابلیت از Action عادی «ویرایش» کاملاً مستقل باشد.

---

# 2. Action جدید

یک Action جدید با عنوان:

> **ویرایش مجدد**

به فرم اعلامیه پرداخت اضافه شود.

رفتار Action فعلی:

> **ویرایش**

نباید با این تغییر تغییر کند.

این دو Action باید دو کاربرد متفاوت داشته باشند:

| Action      | کاربرد                                                 |
| ----------- | ------------------------------------------------------ |
| ویرایش      | ویرایش عادی اعلامیه پرداخت طبق رفتار فعلی سیستم        |
| ویرایش مجدد | اصلاح اطلاعات قابل تغییر در یک اعلامیه پرداخت تأییدشده |

---

# 3. شرط نمایش Action «ویرایش مجدد»

نمایش Action «ویرایش مجدد» **صرفاً بر اساس وضعیت اعلامیه پرداخت** کنترل شود.

اگر وضعیت اعلامیه پرداخت:

> **تأیید شده**

باشد، Action «ویرایش مجدد» نمایش داده شود.

در نمایش Action نباید بررسی شود که آیا ابزار پرداخت قابل ویرایش وجود دارد یا خیر.

یعنی حتی اگر تمام ابزارهای پرداخت دارای گردش باشند، Action همچنان نمایش داده شود.

بررسی اینکه آیا امکان ویرایش مجدد واقعاً وجود دارد، فقط **پس از کلیک کاربر روی Action** انجام شود.

---

# 4. رفتار هنگام کلیک روی «ویرایش مجدد»

هنگام کلیک روی Action:

> **ویرایش مجدد**

سیستم باید ابزارهای پرداخت اعلامیه را بررسی کند.

برای هر ابزار پرداخت مشخص شود که آیا دارای گردش است یا خیر.

### حالت اول: حداقل یک ابزار پرداخت فاقد گردش وجود دارد

اگر حداقل یک ابزار پرداخت فاقد گردش وجود داشت:

* فرم فعلی اعلامیه پرداخت باز شود.
* فرم در حالت **ویرایش مجدد** قرار گیرد.
* فقط ابزارهای پرداخت فاقد گردش نمایش داده شوند.
* فقط موضوعات پرداخت مرتبط با ابزارهای پرداخت فاقد گردش نمایش داده شوند.
* اطلاعات قابل اصلاح آنها در اختیار کاربر قرار گیرد.

### حالت دوم: تمام ابزارهای پرداخت دارای گردش هستند

اگر تمام ابزارهای پرداخت دارای گردش باشند:

* فرم باز نشود.
* هیچ اطلاعاتی تغییر نکند.
* پیام زیر به کاربر نمایش داده شود:

> **همه آیتم‌ها دارای گردش هستند و امکان ویرایش مجدد وجود ندارد.**

---

# 5. فرم ویرایش مجدد

برای قابلیت «ویرایش مجدد» فرم جدیدی ایجاد نشود.

همان فرم فعلی اعلامیه پرداخت استفاده شود، اما با وضعیت:

> **ویرایش مجدد**

ساختار فعلی فرم حفظ شود.

فرم همچنان دارای دو تب باشد:

1. تب ابزار پرداخت
2. تب موضوعات پرداخت

---

# 6. تب ابزار پرداخت در حالت ویرایش مجدد

در این حالت سیستم باید فقط ابزارهای پرداخت **فاقد گردش** را نمایش دهد.

### ابزار پرداخت فاقد گردش

قابل:

* مشاهده
* ویرایش
* تغییر مبلغ
* تغییر اطلاعات مجاز
* حذف

باشد.

### ابزار پرداخت دارای گردش

اصلاً در حالت ویرایش مجدد نمایش داده نشود.

بنابراین کاربر نباید در فرم با ردیف‌هایی مواجه شود که فقط به‌صورت Read Only یا Disabled هستند.

مثال:

```text
اعلامیه پرداخت

ابزارهای پرداخت:

چک 1001 → دارای گردش
چک 1002 → بدون گردش
چک 1003 → دارای گردش
چک 1004 → بدون گردش
```

در حالت ویرایش مجدد فقط موارد زیر نمایش داده شوند:

```text
چک 1002
چک 1004
```

---

# 7. تب موضوعات پرداخت در حالت ویرایش مجدد

موضوعات پرداخت نیز باید بر اساس ابزار پرداخت مربوطه فیلتر شوند.

اگر ابزار پرداخت فاقد گردش باشد:

> موضوعات پرداخت مرتبط با آن نمایش داده و قابل اصلاح باشند.

اگر ابزار پرداخت دارای گردش باشد:

> موضوعات پرداخت مرتبط با آن اصلاً نمایش داده نشوند.

مثال:

```text
چک 1001
دارای گردش
    موضوع A
    موضوع B

چک 1002
فاقد گردش
    موضوع C
    موضوع D
```

در حالت ویرایش مجدد فقط موارد زیر نمایش داده شوند:

```text
چک 1002

موضوع C
موضوع D
```

---

# 8. امکان اضافه کردن موضوع پرداخت جدید

در حالت ویرایش مجدد، **امکان اضافه کردن موضوع پرداخت جدید برای ابزار پرداخت فاقد گردش مجاز است.**

این قابلیت برای سناریوهایی لازم است که کاربر بخواهد تخصیص یک ابزار پرداخت را تغییر دهد.

مثال:

```text
چک B
مبلغ: 200,000,000

قبل:
موضوع A = 200,000,000
```

کاربر می‌تواند در حالت ویرایش مجدد آن را به:

```text
موضوع A = 120,000,000
موضوع B = 80,000,000
```

تغییر دهد.

در این حالت «موضوع B» یک موضوع پرداخت جدید است، اما ایجاد آن مجاز است زیرا به یک **ابزار پرداخت موجود و فاقد گردش** متصل شده است.

همچنین سناریوهای زیر نیز باید مجاز باشند:

```text
موضوع A = 200M

→

موضوع A = 100M
موضوع B = 60M
موضوع C = 40M
```

### محدودیت

موضوع پرداخت جدید:

* باید حتماً به یک ابزار پرداخت موجود و فاقد گردش متصل باشد.
* نباید به ابزار پرداخت دارای گردش متصل شود.
* نباید به‌صورت مستقل و بدون ارتباط با ابزار پرداخت ایجاد شود.

---

# 9. عدم امکان افزودن ابزار پرداخت جدید

در حالت:

> **ویرایش مجدد**

امکان اضافه کردن **ابزار پرداخت جدید** وجود نداشته باشد.

بنابراین:

* دکمه/Action افزودن ابزار پرداخت جدید نمایش داده نشود.
* کاربر نتواند ابزار پرداخت جدید ایجاد کند.
* Backend نیز ایجاد ابزار پرداخت جدید را در این فرآیند قبول نکند.

دلیل:

ویرایش مجدد صرفاً برای اصلاح ابزارهای پرداخت موجود است و نباید باعث ایجاد ابزار پرداخت جدید در یک اعلامیه پرداخت تأییدشده شود.

---

# 10. رابطه ابزار پرداخت و موضوعات پرداخت

ابزار پرداخت و موضوعات پرداخت مرتبط با آن باید در حالت ویرایش مجدد یک مجموعه منطقی در نظر گرفته شوند.

اگر مبلغ ابزار پرداخت تغییر کند، کاربر باید بتواند موضوعات پرداخت مرتبط با همان ابزار را نیز اصلاح کند.

مثال:

```text
چک B
مبلغ: 200,000,000

موضوع A: 120,000,000
موضوع B: 80,000,000
```

کاربر مبلغ چک را به:

```text
250,000,000
```

تغییر می‌دهد.

باید بتواند تخصیص موضوعات پرداخت را نیز تغییر دهد:

```text
موضوع A: 150,000,000
موضوع B: 100,000,000
```

---

# 11. کنترل مجموع موضوعات پرداخت

در زمان ذخیره، سیستم باید کنترل کند:

> **جمع مبالغ موضوعات پرداخت مرتبط با هر ابزار پرداخت = مبلغ همان ابزار پرداخت**

مثال:

```text
مبلغ چک: 250,000,000

موضوع A: 150,000,000
موضوع B: 100,000,000

جمع: 250,000,000
```

در این حالت ذخیره مجاز است.

اگر:

```text
موضوع A: 150,000,000
موضوع B: 80,000,000

جمع: 230,000,000
```

باشد، ذخیره مجاز نباشد.

این Validation باید در Backend نیز انجام شود.

---

# 12. حذف ابزار پرداخت

در حالت ویرایش مجدد:

### ابزار فاقد گردش

امکان حذف داشته باشد.

### ابزار دارای گردش

امکان حذف نداشته باشد.

از آنجا که ابزار دارای گردش در این حالت اصلاً نمایش داده نمی‌شود، کاربر به‌صورت مستقیم امکان حذف آن را نخواهد داشت.

Backend نیز باید این محدودیت را enforce کند.

---

# 13. حذف موضوع پرداخت

برای موضوع پرداخت مرتبط با ابزار فاقد گردش:

* امکان حذف وجود داشته باشد.

برای موضوع پرداخت مرتبط با ابزار دارای گردش:

* هیچ تغییری مجاز نباشد.

---

# 14. رفتار Action «ویرایش»

این تغییر نباید هیچ تأثیری روی Action فعلی:

> **ویرایش**

داشته باشد.

منطق، UI و محدودیت‌های فعلی Edit بدون تغییر باقی بمانند.

قابلیت جدید صرفاً یک Action مستقل است:

> **ویرایش مجدد**

---

# 15. وضعیت فرم در حالت ویرایش مجدد

در حالت ویرایش مجدد بهتر است یک وضعیت مشخص در فرم وجود داشته باشد تا Frontend و Backend بدانند عملیات فعلی از نوع:

> **Re-Edit / ویرایش مجدد**

است.

همچنین می‌توان بالای فرم یک Hint نمایش داد:

> **حالت ویرایش مجدد: فقط آیتم‌های فاقد گردش قابل ویرایش هستند.**

این پیام صرفاً جهت اطلاع کاربر است.

---

# 16. اصل مهم Backend

مخفی شدن ابزارهای دارای گردش در Frontend به هیچ عنوان نباید باعث حذف آنها از اطلاعات واقعی اعلامیه پرداخت شود.

مثلاً:

```text
اعلامیه پرداخت 1001

ابزارهای پرداخت:

A → دارای گردش
B → فاقد گردش
C → دارای گردش
```

در حالت ویرایش مجدد Frontend فقط B را نمایش می‌دهد.

اما اطلاعات واقعی همچنان:

```text
A
B
C
```

است.

پس از اصلاح B:

```text
A → بدون تغییر
B → اصلاح‌شده
C → بدون تغییر
```

اطلاعات A و C نباید حذف یا overwrite شوند.

---

# 17. Partial Update

ذخیره اطلاعات در حالت ویرایش مجدد باید به صورت:

> **Partial Update**

انجام شود.

نباید کل لیست ابزارهای پرداخت از Frontend دریافت و جایگزین اطلاعات قبلی شود.

برای مثال، اگر Frontend فقط ابزار B را ارسال می‌کند:

```text
B → اصلاح شود
```

Backend نباید برداشت کند که A و C حذف شده‌اند.

بلکه باید:

```text
A → بدون تغییر
B → اصلاح شود
C → بدون تغییر
```

را اجرا کند.

---

# 18. کنترل Backend

تمام محدودیت‌های این مستند باید در Backend نیز enforce شوند.

Backend باید حداقل موارد زیر را کنترل کند:

1. اعلامیه پرداخت در وضعیت تأییدشده باشد.
2. عملیات از نوع «ویرایش مجدد» باشد.
3. ابزارهای دارای گردش شناسایی شوند.
4. تغییر ابزار دارای گردش ممنوع باشد.
5. حذف ابزار دارای گردش ممنوع باشد.
6. تغییر مبلغ ابزار دارای گردش ممنوع باشد.
7. تغییر موضوعات پرداخت مرتبط با ابزار دارای گردش ممنوع باشد.
8. حذف موضوعات پرداخت مرتبط با ابزار دارای گردش ممنوع باشد.
9. ایجاد ابزار پرداخت جدید ممنوع باشد.
10. ایجاد موضوع پرداخت جدید برای ابزار فاقد گردش مجاز باشد.
11. ایجاد موضوع پرداخت جدید برای ابزار دارای گردش ممنوع باشد.
12. ایجاد موضوع پرداخت مستقل و بدون ابزار پرداخت ممنوع باشد.
13. تغییر ابزارهای فاقد گردش مجاز باشد.
14. تغییر موضوعات پرداخت مرتبط با آنها مجاز باشد.
15. اطلاعات ابزارهای دارای گردش در زمان ذخیره حفظ شوند.
16. جمع موضوعات پرداخت با مبلغ ابزار پرداخت تطابق داشته باشد.

---

# 19. سناریوی کامل

فرض کنید یک اعلامیه پرداخت تأیید شده شامل موارد زیر است:

```text
ابزار پرداخت:

چک A
مبلغ: 100M
دارای گردش

چک B
مبلغ: 200M
فاقد گردش

چک C
مبلغ: 150M
دارای گردش
```

موضوعات پرداخت:

```text
چک A:
موضوع 1 = 60M
موضوع 2 = 40M

چک B:
موضوع 3 = 200M

چک C:
موضوع 5 = 150M
```

کاربر روی:

> **ویرایش مجدد**

کلیک می‌کند.

سیستم تشخیص می‌دهد که چک B فاقد گردش است.

فرم باز می‌شود.

در تب ابزار پرداخت:

```text
چک B
مبلغ: 200M
```

در تب موضوعات پرداخت:

```text
موضوع 3 = 200M
```

چک‌های A و C و موضوعات مرتبط با آنها نمایش داده نمی‌شوند.

کاربر می‌خواهد چک B را بین دو موضوع تقسیم کند.

مبلغ چک همچنان:

```text
200M
```

است.

موضوعات پرداخت را به شکل زیر تغییر می‌دهد:

```text
موضوع 3 = 120M
موضوع 4 = 80M
```

در اینجا «موضوع 4» یک موضوع پرداخت جدید است.

سیستم کنترل می‌کند:

```text
120M + 80M = 200M
```

و اصلاح را ذخیره می‌کند.

نتیجه:

```text
چک A → بدون تغییر
چک B → اصلاح‌شده
    موضوع 3 = 120M
    موضوع 4 = 80M
چک C → بدون تغییر
```

# 20. سناریوی تغییر مبلغ و ایجاد موضوع جدید

فرض کنیم:

```text
چک B = 200M

موضوع A = 200M
```

کاربر مبلغ چک را به:

```text
250M
```

افزایش می‌دهد.

سپس موضوعات را به شکل زیر اصلاح می‌کند:

```text
موضوع A = 150M
موضوع B = 100M
```

در اینجا:

* تغییر مبلغ چک مجاز است.
* تغییر مبلغ موضوع A مجاز است.
* ایجاد موضوع B مجاز است.
* جمع موضوعات برابر مبلغ چک است.

بنابراین ذخیره مجاز است.

---

# 21. سناریوی بدون امکان ویرایش

فرض کنید اعلامیه پرداخت شامل:

```text
چک A → دارای گردش
چک B → دارای گردش
چک C → دارای گردش
```

است.

کاربر Action:

> **ویرایش مجدد**

را مشاهده می‌کند و روی آن کلیک می‌کند.

سیستم بررسی می‌کند:

```text
آیتم فاقد گردش وجود ندارد.
```

در نتیجه فرم باز نشود و پیام زیر نمایش داده شود:

> **همه آیتم‌ها دارای گردش هستند و امکان ویرایش مجدد وجود ندارد.**

# 22. نکات UI/UX

* Action «ویرایش مجدد» فقط در وضعیت تأییدشده نمایش داده شود.

* بررسی وجود آیتم قابل ویرایش پس از کلیک انجام شود.

# 23. Acceptance Criteria

پیاده‌سازی زمانی کامل است که تمام موارد زیر برقرار باشند:

* [ ] Action جدید با عنوان **ویرایش مجدد** ایجاد شده باشد.
* [ ] Action فعلی **ویرایش** بدون تغییر باقی مانده باشد.
* [ ] Action ویرایش مجدد فقط در وضعیت **تأیید شده** نمایش داده شود.
* [ ] نمایش Action وابسته به وجود آیتم قابل ویرایش نباشد.
* [ ] بررسی وجود آیتم قابل ویرایش پس از کلیک انجام شود.
* [ ] اگر هیچ آیتم فاقد گردش وجود نداشت، فرم باز نشود.
* [ ] در این حالت پیام «همه آیتم‌ها دارای گردش هستند و امکان ویرایش مجدد وجود ندارد.» نمایش داده شود.
* [ ] اگر حداقل یک آیتم فاقد گردش وجود داشت، فرم باز شود.
* [ ] فقط ابزارهای پرداخت فاقد گردش نمایش داده شوند.
* [ ] فقط موضوعات پرداخت مرتبط با آنها نمایش داده شوند.
* [ ] ابزارهای دارای گردش در UI نمایش داده نشوند.
* [ ] موضوعات پرداخت مرتبط با ابزارهای دارای گردش نمایش داده نشوند.
* [ ] مبلغ ابزار فاقد گردش قابل اصلاح باشد.
* [ ] موضوعات پرداخت مرتبط با آن قابل اصلاح باشند.
* [ ] امکان ایجاد موضوع پرداخت جدید برای ابزار فاقد گردش وجود داشته باشد.
* [ ] موضوع جدید حتماً به یک ابزار پرداخت موجود و فاقد گردش متصل باشد.
* [ ] امکان ایجاد موضوع پرداخت برای ابزار دارای گردش وجود نداشته باشد.
* [ ] امکان ایجاد موضوع پرداخت مستقل وجود نداشته باشد.
* [ ] جمع موضوعات پرداخت با مبلغ ابزار کنترل شود.
* [ ] امکان افزودن ابزار پرداخت جدید وجود نداشته باشد.
* [ ] امکان حذف ابزار فاقد گردش وجود داشته باشد.
* [ ] ابزار دارای گردش قابل حذف یا تغییر نباشد.
* [ ] موضوعات پرداخت مرتبط با ابزار دارای گردش قابل تغییر نباشند.
* [ ] Backend تمام محدودیت‌های فوق را enforce کند.
* [ ] اطلاعات ابزارهای دارای گردش حذف یا overwrite نشوند.
* [ ] ذخیره تغییرات به صورت Partial Update انجام شود.
* [ ] ساختار فعلی فرم و دو تب آن حفظ شود.

# 24. نتیجه نهایی

دو مسیر کاملاً مجزا برای کاربر وجود خواهد داشت:

### ویرایش

رفتار فعلی سیستم و بدون تغییر.

### ویرایش مجدد

مخصوص اعلامیه پرداخت تأییدشده.

در این حالت:

> **فقط ابزارهای پرداخت فاقد گردش و موضوعات پرداخت مرتبط با آنها نمایش داده شده و قابل اصلاح هستند.**

در ابزار پرداخت فاقد گردش، کاربر می‌تواند موضوعات پرداخت موجود را اصلاح، حذف یا **موضوع پرداخت جدید اضافه کند**.

اما:

> **ایجاد ابزار پرداخت جدید در حالت ویرایش مجدد مجاز نیست.**

ابزارهای دارای گردش و موضوعات پرداخت وابسته به آنها کاملاً از فرآیند اصلاح خارج هستند و در Backend نیز محافظت می‌شوند.

همچنین مجموع مبالغ موضوعات پرداخت هر ابزار باید همواره با مبلغ همان ابزار برابر باشد.
