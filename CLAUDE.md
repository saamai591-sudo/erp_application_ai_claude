# Accounting ERP — Project Memory

Persian (RTL, Jalali calendar) web accounting/ERP for small–medium businesses. Monorepo: `backend/` (Express + Prisma + PostgreSQL) and `frontend/` (React SPA). UI text, comments, error messages and design docs are in **Persian** — keep new user-facing text and code comments in Persian, consistent with the surrounding code.

Last refreshed: 2026-09-20 (branch `master`; main branch for PRs is `main`).

## Stack & run

- Backend: Node + Express 4 + TypeScript, Prisma 5, PostgreSQL 16, JWT (`jsonwebtoken`, `bcryptjs`), `zod`, `express-async-errors`. Port 4000, all routes under `/api`.
- Frontend: React 18 + TS + Vite 5, `react-router-dom` 6, `react-multi-date-picker` (Jalali), `recharts`, `xlsx`. No UI kit — hand-written components and one `styles.css`. Dev port 5173 (Docker maps 5174).
- Docker: `docker compose up --build` (db on host 5433, backend 4000, frontend 5174; source bind-mounted, watch mode). Frontend derives API URL from `window.location.hostname` unless `VITE_API_URL` is set.
- Backend scripts: `npm run dev` (tsx watch), `build` (tsc), `seed`, `prisma:migrate`, plus maintenance scripts in `backend/src/scripts/` (cleanup-orphans, recompute-has-transactions, goods backfill/backup/restore/delete).
- Frontend: `npm run dev`, `npm run build` (`tsc -b && vite build`). `backend/dist` and `frontend/dist` are untracked build output.
- Default seed login: mobile `0999999999`, password `Admin@123`.
- No test suite exists; verify with `tsc` builds and by using the feature in the browser.
- Migrations: `backend/prisma/migrations/` (~70, timestamped `2026MMDD...`). Schema is `backend/prisma/schema.prisma` (~3000 lines, ~134 models, ~55 enums). Add a new migration for every schema change.

## Backend layout (`backend/src`)

- `index.ts`: registers ~79 route files. Order: public `/api/auth` → `requireAuth` → `fiscalScopeContext` → everything else. Global error middleware at the end.
- `routes/`: one file per form/group; call Prisma directly (no repository layer). Shared business logic lives in `services/` (`journalEntryService` = the single entry point for issuing journal entries, `goodsPricingService`, `warehouseMovementService`, `warehouseStockService`, `warehouseConfirmationService`, `serialLifecycleService`, `batchService`, `documentEffectsService`, `salesReviewService`, `importJobService`, …).
- `utils/`: pure helpers (`coding.ts` auto detail codes, `concurrency.ts`, `currencyConversion.ts`, `vatCalculation.ts`, `jalaliDate.ts`, `tableFilters.ts`, `warehouseTracking.ts`, …).
- `authz/`: RBAC. `registry.ts` is the **single source of truth** for modules/forms/actions (base actions view/create/edit/delete + custom). Routes use `can("module.sub.form.action")` from `guard.ts`; an unregistered key crashes the server at boot. `sync.ts` syncs the registry to DB; the admin permission tree comes from `GET /api/authz/tree`. To add a form/action, edit `registry.ts` (and `navConfig.ts` for menu).
- `middleware/fiscalScope.ts` + `lib/prisma.ts`: frontend sends `x-fiscal-period-id`; the Prisma client wrapper **automatically scopes list queries** of every model having `fiscalPeriodId` to the current fiscal period (fallback: latest period). `bypassFiscalScope` exists in request context for exceptions. Dates of documents must fall in the current fiscal period (`utils/fiscalPeriodValidation.ts`).
- `utils/concurrency.ts`: lost-update protection — GET/:id returns `updatedAt`; PUT/:id calls `assertRecordNotStale(existing.updatedAt, req.body.updatedAt, label)` right after the not-found check. Frontend `lib/api.ts` remembers and re-sends it automatically.
- `importProcessors/` + `ImportJob`: async Excel import per record type.
- `lib/bulkError.ts`: structured bulk-failure errors (`details`) rendered by frontend `BulkErrorDialog`.
- `data/warehouseDocNatureMatrix.ts`: warehouse document nature rules.

## Frontend layout (`frontend/src`)

- `App.tsx` routes (list/new/edit per form), `navConfig.ts` menu, `pages/` (~95 files, one per form/report), `components/` shared (DataTable, Modal, FormPage, TreeView, RecordPicker, JalaliDatePicker, AmountInput, FxAmountDialog, Wizard, TabsBar, …), `lib/` (api, AuthContext, TabsContext, `useCrud`, `useDocumentForm`, `usePermissions`, formatters, review-report caches, `currencyConversion`, `vatCalculation`, `costAllocation`).
- Server is the source of truth; frontend only does display-side helper calculations.
- Submodule order (general rule, all modules): «تنظیمات» first, operations/other groups in their defined order in the middle, «گزارش…» last. Enforced centrally — `MODULES` in `frontend/src/navConfig.ts` and `sortSubModules` in `backend/src/authz/registry.ts` (permission tree) — so the definition order in those arrays doesn't matter; new submodules just need the right title.
- Keyboard (shared components): every selector dialog (`RecordPicker`, `MultiRecordPicker`, hook `components/pickerKeyboard.ts`) supports ↑/↓ (PageUp/PageDown) to move the highlighted row, Enter to select it (multi-select: Enter ticks, Ctrl+Enter confirms), Esc to close; the first filter box is auto-focused so "type a filter, press Enter" picks the first match. `FormPage` binds Ctrl+S/Cmd+S to the toolbar Save button (skipped while a dialog is open or when Save is disabled). New selectors/forms should reuse these components rather than re-implementing keys.
- Description defaults in Payment/Receipt forms: a new instrument row starts with the header description (on new documents, typing the header description also updates instrument rows that still hold the default); loading an instrument into the subjects grid copies its description to the subject row. Payment subject amount defaults from the instrument's remaining amount for no-basis types.
- Sales delivery (حواله فروش) basis: NO_BASIS / SALES_ORDER / SALES_QUOTE (پیش‌فاکتور). Quote-based lines store `InventoryDocumentLine.sourceSalesQuoteLineId` (enum `InventoryBasis.SALES_QUOTE`); a quote line's deliverable remaining = quantity − quantity converted to sales orders − quantity delivered directly; the sales-order quote picker also subtracts direct deliveries, and a quote with direct deliveries can't be unapproved. The quote's customer must match the header party's customer.
- Sales invoice price call-through from the delivery's base document (فراخوانی قیمت در فاکتور; spec `Documents/فراخوانی قیمت در فاکتور.md`): for a `SALES_DELIVERY`-basis invoice line whose source delivery line was itself issued on `SALES_ORDER`/`SALES_QUOTE` basis (`InventoryDocumentLine.sourceSalesOrderLineId`/`sourceSalesQuoteLineId`), `unitPrice`/`amount` are no longer user-entered — `routes/salesInvoices.ts#validateLines` always recomputes and overwrites them (ignoring whatever the client sent), on both create and edit. `salesOrderLineUninvoiced`/`salesQuoteLineUninvoiced` (mirroring `salesDeliveries.ts`'s own `salesOrderLineRemaining`/`salesQuoteLineRemaining`, but summing *invoiced* qty/amount — via each delivery line's `salesInvoiceLines`, across every delivery drawn from that order/quote line — instead of *delivered*) give the order/quote line's uninvoiced remaining; `deliveryLineBaseInfo` picks whichever of the two the delivery line actually used and returns it with the order/quote's own currency/salesType. Unit rate = uninvoiced amount ÷ uninvoiced quantity (computed once per distinct order/quote line per save and reused across every invoice row referencing it, even via different delivery lines); invoice line amount = that rate × the row's quantity. The invoice's header currency and salesType must equal the base document's (rejected otherwise — a delivery has neither field itself). A NO_BASIS delivery (no order/quote behind it) is untouched — price stays user-entered, exactly as before. This is a DB-derived lock, not a flag: nothing new is stored on `SalesInvoiceLine`, since the source delivery line's own `sourceSalesOrderLineId`/`sourceSalesQuoteLineId` (persisted at delivery-creation time) is re-read and reapplied on every save, including edits. `GET /sales-invoices/pickable-sales-delivery-lines` returns a `base` field (currency/salesType titles+ids, base amount/quantity, uninvoiced amount/quantity, `null` for NO_BASIS deliveries) so the picker can show it; `SalesInvoices.tsx`'s picker columns display it and the fی/مبلغ (`unitPrice`/`amount`) `AmountInput`s are `disabled` (with an explanatory `title`) whenever the picked row has a `base` — purely a UX mirror of the server-side lock, computed live from `pickableLines`, not a stored row flag.
- Sales invoice void action (ابطال؛ scoped to SalesInvoice only, per explicit user decision — no other invoice-like document has this yet): `POST /sales-invoices/:id/void` (permission `sales.operations.sales-invoices.void`) is a plain status flip to `VOIDED` (new value on the shared `SalesDocStatus` enum — SalesQuote/SalesOrder/SalesReturnInvoice share the enum but no code writes `VOIDED` on them) — no mirror/reversal document, no separate voiding process, matching the explicit spec. Allowed only when the invoice has neither an issued journal entry (`journalEntryId`) nor any row referencing it as a transaction — checked by counting `ReceiptSettlementLine`/`PaymentSettlementLine`/`SalesInvoiceAdvanceAllocation`/`PettyCashPayment`/`PettyCashSummaryLine` rows with this `salesInvoiceId` (there's no existing combined helper for this; the four other invoice-like documents — PurchaseInvoice/ServicePurchaseInvoice/SalesReturnInvoice — only guard delete on `journalEntryId`, so this check was written from scratch here and isn't shared). Once voided, the invoice is fully locked: edit/delete/`issue-journal-entry` all reject with `status === "VOIDED"` guards, and `SALES_INVOICE_ADVANCE_LOCKS` (`services/salesInvoiceAdvanceService.ts`) gained a `VOIDED` entry so advance-allocation edits reject too (same extensible-array pattern as `PAYMENT_FLOW`/`JOURNAL_ENTRY`). Frontend (`SalesInvoices.tsx`): `locked` now also covers `status === "VOIDED"` (fieldset + save disabled, same as the journal-entry lock); the «ابطال» button (`VoidIcon`, same shape as `ChequeBookLeaves.tsx`'s) sits next to «صدور سند حسابداری» (only shown pre-JE, pre-void) with a `window.confirm`; the list and the edit-form header both show a «وضعیت» column/field (`SALES_INVOICE_STATUS_FA`). Two additional consumer-side exclusions per spec: `services/salesReviewService.ts#getSaleLines` filters `salesInvoice.status: { not: "VOIDED" }` (Sales Review has no other status filtering — SalesInvoice.status was otherwise a dead field, since this invoice never had an approve step); and the two SALES_INVOICE basis-candidate sources that feed "the shared invoice selector" — `services/paymentBasisCandidates.ts` (Payments/PettyCashPayments) and `routes/receipts.ts`'s own local `candidatesForBasisType` (Receipts) — both default-exclude `status: "VOIDED"` with an `includeVoided` opt-in parameter (per spec: "exceptions explicitly configured at the relevant usage," currently unused by any caller). There is no single centralized "Invoice Selector" component/endpoint in this codebase (`RecordPickerField` is a generic UI shell reused per-site; each site owns its own backend candidate query) — a future invoice type needing the same exclusion must add its own `status`-filter at its own candidate source(s), same as these two.
- Accounting procedures & settings (`Documents/رویه ها و تنظیمات حسابداری.md`; menu حسابداری › تنظیمات › «رویه‌ها و تنظیمات حسابداری», route `/accounting-settings`, permission form `accounting.settings.accounting-settings.*`): a tabbed page (tabs: تنظیمات ارز, ارزش افزوده; add a tab = new entry in `TABS` + a `DatedSettingConfig` in `pages/AccountingSettings.tsx`). All settings are date-based — each record has a unique start date and the effective value for a date is the latest record with startDate ≤ that date (`services/accountingSettingsService.ts`: `getVatRatePercentForDate`, `getAdvanceReceiptMethodForDate`, cached 60s, invalidated on writes). VAT engine: `resolveVatRatePercent(goodsItem, defaultRatePercent)` no longer has a fixed 10% — every VAT-computing validator (purchase/service-purchase/sales/sales-return invoices, quotes, orders) receives the document date and passes `await getVatRatePercentForDate(docDate)` (a special item's own rate still wins); frontend forms use `useVatRates()`/`vatRateForDate` for live display only. A migration seeds one initial 10% record (2000-01-01) so existing behavior is unchanged; at least one VAT record must always exist and a date with no record raises an error. The advance-receipt FX recognition method (`AdvanceReceiptFxMethod`) is consumed by the sales-invoice advance allocation journal entry (see Domain conventions).
- Fiscal-year date fields (base behavior): every document-date `JalaliDatePicker` gets the prop `fiscalYear` — it limits the calendar to the user's selected fiscal period (`minDate`/`maxDate`, days outside disabled; manually typed out-of-range dates get a red border + tooltip) via `lib/useSelectedFiscalPeriod.ts` (one shared cached `/fiscal-periods` fetch). New document forms just add `fiscalYear` to their date picker. Backend enforcement is the truth: `assertWithinCurrentFiscalPeriod(periodId)` / `assertDateWithinCurrentFiscalPeriod(date)` in `utils/fiscalPeriodValidation.ts` (message includes the period range); use one of them in every route that accepts a document date.
- Default currency (base rule): every «ارز» field of a new document defaults to the base currency. Header currency selects use the hook `lib/useDefaultBaseCurrency.ts` (`enabled: !editId && loaded`, fills only an empty value, never overwrites the user's choice or an existing document); Receipts/Payments give new CASH instrument rows the base currency (bank-transfer rows take their bank account's currency, cheques are always base); journal-entry lines and treasury-opening cash rows already start on base. A new form with a currency select must use the hook.
- Multiple new forms at once (base behavior, `lib/TabsContext.tsx` + `lib/usePersistedState.ts`): opening a `/new` form whose path is already open in a tab creates another tab with the unique path `…/new?_i=<n>` instead of jumping to the existing one; `usePersistedState`/`hasPersistedState` transparently rewrite `form:<pathname>…` keys to `form:<pathname>@<n>…` for such tabs so each keeps independent state, and `clearFormState` clears only that instance. `/edit` forms stay one tab per record. Pages need no changes.
- Cheque document reviews («مرور اسناد دریافتنی/پرداختنی», treasury › گزارش; spec `Documents/تغییرات نقدینگی و چک راه اندازی مرور اسناد دریافتی و پرداختی.md`): one page `pages/ChequeDocumentsReview.tsx` (prop `kind`), routes `routes/chequeReview.ts` (`/cheque-review/:kind/statuses|cheques|details`), data `services/chequeReviewService.ts` — no duplicated data: events are read from approved receipts/payments/deposits/deposit-returns/clearings (+ opening) of each `ChequeItem`; a cheque is listed if any of its events falls in the range; the range must lie inside ONE fiscal period (`assertSingleFiscalPeriod`, also checked in the page). Chained tabs وضعیت ← اسناد ← جزئیات. Receipt cheque instrument rows require a cash box (`cashBoxId`, validated in `cleanOneInstrumentLine`; cash review still counts CASH rows only).
- Base grids always show their column headers, also when empty or loading (`DataTable`, `SelectableBalanceTable` render the message inside the table body). Note: the automatic «شماره سند حسابداری» column of `DataTable` still needs at least one row to be detected.
- Purchase review («مرور خرید», زنجیره تامین › گزارش, `/purchase-review`): clone of the sales review (`pages/PurchaseReview.tsx`, `routes/purchaseReview.ts`, `services/purchaseReviewService.ts`, cache `lib/purchaseReviewCache.ts`) with tabs نوع خرید, تامین‌کننده, گروه کالا (per level), گروه حسابداری, کالا, اسناد, گردش (no sales-center equivalent). Purchases = lines of APPROVED `PurchaseInvoice`s (base-currency `baseAmount/baseDiscount/vatAmount`); returns = `SUPPLIER_RETURN` inventory lines (quantity; amount from `getLineAmounts`, no discount/VAT, purchase type shown as «نامشخص»); service purchase invoices are not included. Supplier dimension is keyed by party id. The purchase-invoice list also shows مبلغ / تخفیف / ارزش افزوده / خالص (`listAmounts` in `routes/purchaseInvoices.ts`, VAT ÷ invoice fxRate).
- Fiscal-period chain (`routes/fiscalPeriods.ts`, `pages/FiscalPeriods.tsx`): a new period's start date is forced server-side to be exactly the day after the latest period's end (no gap/overlap); create and the last period's end-date edit run in one transaction under a Postgres advisory lock (`FISCAL_CHAIN_LOCK_KEY`) so concurrent requests can't break the sequence. The new-period form auto-fills and locks the start date (editable only for the very first period) and defaults the end date to one day before the same Jalali date next year (leap years give 12/30); the end date stays editable.
- Journal-entry renumbering (single source of truth: `services/journalEntryRenumberService.ts` → `renumberJournalEntries(fiscalPeriodId, tx?)`): all DRAFT/REVIEW entries of the period are re-numbered contiguously (`number` only) starting after the highest APPROVED number, ordered by date → dailyNumber → id (two raw-SQL steps under a Postgres advisory lock; temporary negative numbers avoid the `(fiscalPeriodId, number)` unique clash). `referenceNumber`/`dailyNumber` and approved entries are never touched. Two callers, no duplicated logic: the «شماره‌گذاری مجدد» item of the journal-entries list «عملیات» menu (`POST /journal-entries/renumber`, permission `accounting.operations.journal-entries.renumber`; DataTable bulk action with `noSelection: true` = always enabled, no row selection needed) and document confirmation (`POST /document-confirmation/confirm` runs renumber + approve in ONE transaction; the page asks «اسناد تا این تاریخ شماره‌گذاری مجدد خواهند شد» before confirming). Any future caller must use the service, never re-implement it.
- Journal-entry delete guard (central, `lib/prisma.ts`): the shared Prisma client rejects `journalEntry.delete/deleteMany` for entries in status REVIEW or APPROVED (`JOURNAL_ENTRY_LOCKED_DELETE_MESSAGE`) — it also works inside `$transaction([...])` — so every source document's «حذف سند حسابداری» (sales/purchase invoices, treasury, warehouse, account closing, opening/closing …) is covered without per-route checks. Editing manual entries is DRAFT-only in `routes/journalEntries.ts`.
- Sidebar text fitting: module/submodule/item labels in `Layout.tsx` use `components/FitText.tsx`, which shrinks only an overflowing label's font in 0.5px steps down to a 10px minimum (then ellipsis + tooltip), re-measuring on every render, on parent resize (ResizeObserver) and after fonts load. Other labels keep their CSS size. Use it for any new single-line label that must never be truncated.
- Collapsible sidebar (`Layout.tsx`): a toggle button (`.sidebar-toggle-btn`, next to the title) switches the sidebar between the full accordion and a `.sidebar-collapsed` icon-only rail (`.module-icon-btn` per module — every module has its own distinct icon+color in `MODULE_ICON`/`--nc-mod-*`, no fallback sharing). In collapsed mode, clicking a module icon opens `ModuleFlyout` — a floating panel positioned via `getBoundingClientRect()` of the clicked icon and rendered with `createPortal(..., document.body)` (same reasoning as `Modal.tsx`: the sidebar's `overflow-y: auto` would otherwise clip/misplace it). Per explicit user decision (matched to a specific reference screenshot) the flyout is two-level and cascading — a second panel beside the first, not a replacement of it: panel 1 (own internal `activeSubTitle` state, not lifted to `Layout`) always shows only the module's submodule rows (`.nav-flyout-submodule-row`, no forms); clicking one opens panel 2 next to it (positioned from panel 1's own measured `getBoundingClientRect()` via a `useLayoutEffect`, not a guessed width) showing that submodule's forms — both panels stay visible together. The whole flyout (both panels) closes on outside click (outside *both* panels) or Escape. State: `sidebarCollapsed` persists per-device in `localStorage` (`sidebar-collapsed` — a UI convenience, not a synced user preference like font/theme in `preferences.ts`); on any viewport ≤768px (`matchMedia`, checked on mount and on a live `change` listener) collapsed is forced `true` regardless of the stored preference, per explicit user decision that icon-only is always the mobile default. Expanding is still a manual, unrestricted user action even on mobile.
- Treasury year close → next-year opening (`services/treasuryYearCloseService.ts`, `routes/treasuryOpenings.ts`, `pages/TreasuryOpenings.tsx`; spec `Documents/افتتاحیه دریافت و پرداخت و بستن سال.md`): closing a section (bank accounts / cash boxes / receivable cheques / payable cheques, or «بستن همه») immediately creates its records in the next fiscal year's opening. The created records are **system-generated and read-only for the user**: bank/cash opening rows carry `isSystemGenerated` (set by the close, also when it replaces a manual row; a migration backfilled rows of already-closed sections), transferred cheques are the opening cheques with `parentChequeId`. `PUT /treasury-openings/:id` keeps them untouched (`syncBankLines`/`syncCashLines`/`syncCheques`) and rejects any edit or removal with a clear message; manual rows (initial deployment) stay editable next to them. The screen shows them disabled with a «ایجادشده توسط بستن سال» badge / «قفل» (API fields `systemGenerated`, `transferred`, `locked`). The only way to remove them is **Reopen** on the section's row in Period-End Operations (`POST /treasury-year-close/<section>/reopen`, permission actions `reopen*`, `reopenSection` in the service): it deletes that section's system-generated rows/cheques from the next year's opening, removes the close record (so the section can be closed again) and deletes the next opening itself when nothing is left in it. It refuses when a transferred cheque already has a document/movement in the next year (nothing is deleted) or when the next year has its own closes. `DELETE /treasury-openings/:id` is rejected for an opening the previous year's close created or that has system-generated content (`isOpeningDeletionBlocked`; detail field `deletable:false` hides the delete menu); an opening made only of manual rows stays deletable. The Period-End screen has one row per section with **Close** (enabled when open) and **Reopen** (enabled when closed) — there is no «view next year opening» button; a manual row for the same bank account/cash box that a close replaced is removed by the reopen along with it.
- Frequently used descriptions («شرح‌های پرکاربرد», اطلاعات پایه › تنظیمات, `/frequent-descriptions`, `routes/frequentDescriptions.ts`, `pages/FrequentDescriptions.tsx`, model `FrequentDescription`, permission form `master-data.settings.frequent-descriptions.*` with view/edit/delete only): reusable `components/DescriptionField.tsx` replaces the header «شرح» `<label>`+`<input>` pair in the document/master forms (a save icon next to the input + suggestions while typing). A record = **form key + field key + text** shared by all users; `formKey` is derived from the page URL through `navConfig` (`lib/frequentDescriptionForms.ts`: `/payments/new` → `payments`), so a new form only needs to use `<DescriptionField>`; `fieldKey` defaults to `description`. Saving is always an explicit click (`POST /frequent-descriptions`, login only, no per-form permission); text is trimmed/whitespace-collapsed, max 500 chars, and a unique index on (formKey, fieldKey, text) makes a repeat save a no-op (`created:false`). Suggestions: `GET /frequent-descriptions?formKey&fieldKey&q` (contains, starts-with first, newest first, max 8) — only that form+field. The management form (list + edit page, no «new» — records come from the forms) uses `GET /frequent-descriptions/manage`, `PUT/DELETE /frequent-descriptions/:id` (permission-guarded; editing to an existing text of the same form+field is rejected).
- Petty cash definition («تنخواه», مدیریت خزانه › تنظیمات, `/petty-cashes`, `routes/pettyCashes.ts`, `pages/PettyCashes.tsx`, model `PettyCash`, permission form `treasury.settings.petty-cashes.*`): fields detail code / title / currency / limit (`limitAmount`, in the petty cash's own currency) / active. The detail code is issued only by the general detail-code service (`generateDetailCode(5)` + `registerDetailCode(..., "PettyCash", id)` from `utils/coding.ts`, detail type 5 «تنخواه»); the API ignores any code sent by the client and the form shows it read-only. The currency defaults to the base currency for new records (`useDefaultBaseCurrency`) and can't change once `hasTransactions`; `GET /petty-cashes?activeOnly=true` is for future selectors. No transactions use it yet.
- Petty cash custodian («تنخواه‌دار», treasury › تنظیمات, `/petty-cash-custodians`, `routes/pettyCashCustodians.ts`, `pages/PettyCashCustodians.tsx`, model `PettyCashCustodian`, permission form `treasury.settings.petty-cash-custodians.*`): detail code (issued by the general detail-code service, `generateDetailCode(6)` + `registerDetailCode`, never client-supplied) / petty cash / party / active / `controlNegativeBalance` (default true — per-custodian, see running-balance control below). Unique per (petty cash, party); petty cash and party must be active when chosen; petty cash/party can't change once `hasTransactions`; a petty cash that has custodians can't be deleted.
- Petty cash payment («پرداخت تنخواه», treasury › پرداخت, `/petty-cash-payments`, `routes/pettyCashPayments.ts`, `pages/PettyCashPayments.tsx`, model `PettyCashPayment`, permission form `treasury.payment-ops.petty-cash-payments.*`): a single-line document (no journal entry, no approve workflow, by explicit user decision) with date / active petty cash custodian / petty cash currency (display-only, from custodian.pettyCash) / payment type / basis (display-only, the selected payment type's own fixed `basisType` — never user-chosen) / party (always shown; must be a supplier for PURCHASE_INVOICE/PURCHASE_ORDER, a customer for SALES_INVOICE) / a base-document picker when basisType≠NONE / amount / description. Base-document controls mirror the Payment form's «موضوعات پرداخت» (by explicit user decision): the base document's date must be less than the payment's date, the base document's currency must equal the petty cash's currency (this form has no per-row FX, unlike Payments), the amount can't exceed the base document's remaining, and once a base document is picked the frontend disables the Date field (clear the base first to change it). The base-document "remaining" logic (`services/paymentBasisCandidates.ts`, `candidatesForBasisType`) is shared with `routes/payments.ts`'s settlement rows so a purchase/sales invoice or purchase order can't be over-consumed across the two independent documents — extracted from Payments during this feature; both routes call the same function (`{excludePaymentId}`/`{excludePettyCashPaymentId}`). Negative-balance control (`services/pettyCashBalanceService.ts`, `assertPettyCashRunningBalanceNotNegative`): if the payment's custodian has `controlNegativeBalance`, the petty cash's true chronological running balance (see below) must never go negative at any point in the event sequence; checked on create/edit (excluding the record being edited) and also on Payment edit/delete/re-edit when it removes/changes a TO_PETTY_CASH funding line (unapprove doesn't change the balance).
- Petty cash summary («خلاصه تنخواه», treasury › پرداخت, `/petty-cash-summaries`, `routes/pettyCashSummaries.ts`, `pages/PettyCashSummaries.tsx`, models `PettyCashSummary`/`PettyCashSummaryLine`, permission form `treasury.payment-ops.petty-cash-summaries.*`): posts registered Petty Cash Payments into real GL accounts. Two-step like Payments (`TreasuryDocStatus` DRAFT→APPROVED, then a separate manual «صدور سند حسابداری»/«حذف سند حسابداری» pair — `services/pettyCashSummaryJournalEntryService.ts`); no `reEdit` action (not requested). Header: date / petty cash custodian / petty cash currency (display-only, from custodian.pettyCash) / exchange rate (`fxRate`, forced to 1 server-side when the petty cash's currency is base — same rule as every other base-currency document) / description. Whole document (header+lines) saved in one POST/PUT, exactly like Payments/JournalEntries — the toolbar's «بارگذاری پرداخت‌های تنخواه» button (no selector: on click it loads every one of the custodian's payments that still has an unallocated remaining, given the form's current rows), per-row «تقسیم» (split) button and «تغییر نوع پرداخت» dialog are all client-side state edits included in the next save, not separate endpoints. Each line references one PettyCashPayment (`pettyCashPaymentId`); multiple lines may reference the same payment (split) as long as their sum, across every summary that ever references it (not just this one — `services/pettyCashSummaryRemaining.ts`), never exceeds that payment's own amount. A line's own Payment Type/basis document initially copy the referenced payment's, but can be changed independently per line (the party used for basis lookups always stays the payment's own party — there's no separate party field on the line). Main Account is never chosen directly: it's resolved from the line's Payment Type + basis document by `services/paymentSubjectAccount.ts` — the exact NONE/PURCHASE_INVOICE/SALES_INVOICE/PURCHASE_ORDER rules used by `paymentJournalEntryService.ts`'s settlement-line debit side (extracted from there during this feature so both share one implementation; TO_BANK/TO_CASH_BOX/TO_PETTY_CASH natures are excluded everywhere a petty cash payment type is chosen, since neither Petty Cash Payment nor this form carries a bank-account/cash-box/custodian field to resolve those). Detail 1/2/3 are the one thing that IS manually picked per line, exactly like a journal-entry line (`RecordPicker` limited to the resolved account's configured detail types; mandatory-detail presence is checked the same way as `routes/journalEntries.ts`'s `validateAccountForLine`). Exchange revaluation: computed and stored on each line only at approve time, only for PURCHASE_INVOICE/SALES_INVOICE-basis lines, via the existing `calculateExchangeGainLoss` formula (header `fxRate` vs. the basis document's own historical rate) — matching Payments' settlement-row treatment. The credit side is one line per document: a new `TreasuryAccountSetting` type `PETTY_CASH` (target field `pettyCashId`, wired into `routes/treasuryAccountSettings.ts`'s existing generic `TARGET_FIELD` mechanism) maps each petty cash to a control account, detailed by the petty cash's own `detailCode`, credited for the document total.
- Bank account selection (shared component `components/BankAccountPicker.tsx`): wherever a bank account is chosen, use `BankAccountPicker` (dialog columns «کد تفصیلی» / «عنوان تفصیلی», hidden `bankAccountId` input, `onChange(id, account)`, optional `filter`, e.g. `hasChequeBook`). Its data is `GET /banking/accounts`, which returns `detailTitle` from the single backend helper `bankAccountDetailTitle` (utils/detailValues.ts). Don't build ad-hoc bank account `<select>`s.
- Accounting document number in lists (base rule, `components/DataTable.tsx`): any list whose rows carry `journalEntryReferenceNumber` (global reference number of the issued journal entry, `null` if not issued — always return the key, e.g. `d.journalEntry?.referenceNumber ?? null`) automatically gets a last column «شماره سند حسابداری» (numeric filter/export included). Never define that column per page; a new form that issues journal entries only needs its list API to return the field.

## Domain conventions & gotchas

- Dates stored Gregorian in DB, shown Jalali. Amounts are `Decimal`, never float. Foreign-currency lines carry a rate and base-currency equivalents (`baseDebit/baseCredit`, base-currency VAT); FX gain/loss (تسعیر) is centralized.
- Journal entries: 3 numbers (per-fiscal-period number, global ref number, daily number); must balance in base currency; status DRAFT/REVIEW/APPROVED; `JournalEntrySource` links back to the issuing document; `IssuingSystem` enum marks the issuing module. `journalEntryService.issueJournalEntry` itself enforces mandatory detail 1/2/3 (per the account's configured detail types) for every line, for every caller — the only account-specific check centralized there; level/no-children/currency-vs-base remain the caller's job. The manual journal-entry PUT/edit route (`routes/journalEntries.ts`) doesn't call this service (direct Prisma transaction) so it still keeps its own copy of the same detail check.
- Detail codes (تفصیلی) are globally unique across all detail types via `DetailCodeUsage`.
- `hasTransactions` flag on base entities blocks deletion of records with activity.
- Soft "warning" pattern: HTTP 409 with `{error, warning:true}`; client re-sends with `confirmDuplicate: true`.
- Errors are returned as `{ error: "Persian message" }`. Business rules go inside handlers; `can()` only checks permission.
- Warehouse documents have a status lifecycle, confirmation, date-lock (`assertDateNotConfirmed`, `assertWarehouseOpenForDate`), serial/batch tracking, pricing engine (see docs), and separate JE issuance from warehouse documents.
- Treasury: masters live in خزانه‌داری > تنظیمات (receipt/payment types, received/payable cheque types, "تعیین حسابهای معین" = TreasuryAccountSetting mapping bank account / cash box / cheque type / receipt-payment subject / FX_GAIN_LOSS to a last-level account, "دسته چک" = ChequeBookLeaf per-leaf cheque-book register). Receipt journal entry = manual "issue" action on an APPROVED receipt (`services/receiptJournalEntryService.ts`, issuingSystem TREASURY, doc type RECEIPT): debit per instrument row, credit per settlement row by basis, FX gain/loss on one FX_GAIN_LOSS account; the receipt is locked (no unapprove/edit-approved) until the entry is deleted. The Payment form mirrors the Receipt form (per-row currency/rate, settlement rows with payment types and base documents, FX gain/loss, payable cheque types, issue/revert journal entry via `services/paymentJournalEntryService.ts`, doc type PAYMENT); its cheque rows can also endorse an existing receivable cheque (ChequeItem stores receivableChequeTypeId/payableChequeTypeId for accounting). "دسته چک" (`routes/chequeBookLeaves.ts`): bank accounts whose `BankAccountType.hasChequeBook` is true require picking a RAW leaf (not free-text) when issuing a new cheque in Payments; the leaf flips RAW→ISSUED when the ChequeItem is created (approve / edit-approved) and back to RAW when it's deleted (unapprove / edit-approved); voiding (RAW→VOID) is a separate manual action, only from RAW.
- Treasury year-end (Documents/افتتاحیه دریافت و پرداخت و بستن سال.md): `ChequeItem` belongs to a fiscal period (`fiscalPeriodId`, so every list/picker of cheques is auto-scoped to the current year by the Prisma wrapper) and carries `parentChequeId`/`isOpening`. "افتتاحیه دریافت و پرداخت" (menu: «عملیات اول دوره», first item of Operations; `routes/treasuryOpenings.ts`, `TreasuryOpening*`): one per fiscal period with 4 tabs — opening cheques (= ChequeItems with isOpening), bank-account and cash-box opening balances. "بستن سال دریافت و پرداخت" (menu: «عملیات پایان دوره»; `services/treasuryYearCloseService.ts`, `routes/treasuryYearClose.ts`) closes each section (banks, cash, receivable cheques, payable cheques, or all) of the current year into the NEXT year opening (new cheque with same number + parentChequeId; a section can be closed once; deleting the next-year opening reopens it). Bank/Cash Review (`services/bankAccountReviewService.ts`, `cashReviewService.ts`) are limited to the fiscal period of the from-date and take their opening balance from that period opening.
- Cheque deposit (واگذاری به بانک) journal entry: manual "issue" action on an APPROVED deposit (`services/chequeDepositJournalEntryService.ts`, doc type CHEQUE_DEPOSIT): debit one line (total) on the bank account's "اسناد در جریان وصول" account (new TreasuryAccountSetting type `CHEQUE_IN_COLLECTION`, target = bank account), credit per cheque on the received-cheque account of its type (detail = cheque party). Once issued the deposit is fully locked (no unapprove/edit/delete/re-edit) until the entry is deleted. Cheque deposit return (برگشت از واگذاری) has the mirror voucher (`services/chequeDepositReturnJournalEntryService.ts`, doc type CHEQUE_DEPOSIT_RETURN): debit per cheque on its received-cheque account, credit per bank account on its "اسناد در جریان وصول" account (bank = the approved deposit line that put the cheque in collection); same full lock while the entry exists. Receivable clearing (وصول و برگشت چک دریافتنی) has its voucher too (`services/chequeClearingReceivableJournalEntryService.ts`, doc type CHEQUE_CLEARING_RECEIVABLE): credit per bank account on "اسناد در جریان وصول" (total of all cheques); debit per bank account on the bank ledger account (`BANK_ACCOUNT` setting) for CLEARED cheques, and per cheque on the received-cheque account (party detail) for BOUNCED ones — there is no separate bounced-cheque account, and bank fees are not handled. The bank of each cheque is resolved by the shared `services/chequeDepositBankLookup.ts`. Payable clearing (وصول و برگشت چک پرداختنی) has its voucher too (`services/chequeClearingPayableJournalEntryService.ts`, doc type CHEQUE_CLEARING_PAYABLE): debit per cheque on the payable-cheque account (party detail); credit CLEARED cheques per issuing bank on the bank ledger account (`BANK_ACCOUNT` setting), and BOUNCED cheques per cheque on the new target-less setting `BOUNCED_PAYABLE_CHEQUE` («چک پرداختیِ برگشتی (بدهی به طرف حساب)», one record, party detail) — it must be defined in «تعیین حسابهای معین» before issuing a bounced-cheque voucher.
- Instrument rows used by subjects are locked (Receipts + Payments): while any settlement (subject) row references an instrument row (`instrumentClientKey`), the row is `inert`/faded with a 🔒 hint and can't be edited or deleted in the form; the user must delete the related subject rows first. Backend enforces it on PUT via `utils/instrumentLock.ts` (`assertUsedInstrumentsUnchanged`: an existing instrument line still referenced by incoming subjects must equal its stored values; new unsaved rows and rows whose subjects were removed are free).
- Payment types (نوع پرداخت) have a «ماهیت پرداخت» (nature). Natures TO_BANK («به بانک») / TO_CASH_BOX («به صندوق») / TO_PETTY_CASH («به تنخواه») take no معین and only basis NONE: in the Payment form's settlement rows the account selector lists only bank accounts / cash boxes / petty cash custodians (`PaymentSettlementLine.bankAccountId/cashBoxId/custodianId`, `partyId` is null), and the voucher debits the معین mapped to that bank account / cash box / custodian's petty cash in «تعیین حسابهای معین» (BANK_ACCOUNT / CASH_BOX / PETTY_CASH) with the bank/cash/custodian as detail. TO_PETTY_CASH funds a petty cash (company → custodian); it's excluded from Petty Cash Payment's and Petty Cash Summary's own payment-type pickers (same reason as TO_BANK/TO_CASH_BOX: those forms have no matching field to resolve the row's account against). Bank/cash review reports do not yet count these settlement rows.
- Petty cash review («مرور تنخواه», treasury › گزارش, `/petty-cash-review`, `routes/pettyCashReview.ts` + `services/pettyCashReviewService.ts`, `pages/PettyCashReview.tsx`, `lib/pettyCashReviewCache.ts`, permission form `treasury.reports.petty-cash-review.view`): same pattern as Cash Review («مرور صندوق») with three chained tabs — «تنخواه» (per petty cash: opening / شارژ / پرداخت / closing), «تنخواه‌دار» (same per custodian; filtered by the petty cashes selected in tab 1), «گردش» (flat server-paged ledger with running balance; filtered by the selections of tabs 1–2; double-click opens the Payment or the Petty-cash payment). Movements: شارژ = `TO_PETTY_CASH` settlement lines of **APPROVED** Payments (dated by the payment date); پرداخت = every `PettyCashPayment` (no approval workflow). Amounts are in the petty cash's own currency (not base); no opening/year-close for petty cash, so the opening balance is the sum of all earlier movements across fiscal years (fiscal scope removed with `withoutFiscalPeriodScope`); same-day funding is ordered before spending, like the negative-balance control. The report reads approved funding only (like every review report) while the control counts saved funding too — a saved-but-unapproved funding payment is therefore not in this report yet.
- Petty cash running-balance model (`services/pettyCashBalanceService.ts`, `assertPettyCashRunningBalanceNotNegative`): `PettyCash.limitAmount` is a config value only, never the available balance — per explicit user decision, the running balance always starts at **zero**, not at the limit. Balance at any moment = 0 + Σ funding (`TO_PETTY_CASH` payment-settlement lines of every saved Payment — status DRAFT («ثبت») or APPROVED, each dated by its payment's date; a saved payment already announces the amount to the petty cash, so waiting for approval must not hide it — by explicit user decision after a false «negative balance» rejection of a spend covered by a saved-but-unapproved funding payment) − Σ spending (`PettyCashPayment` records, dated by their own date), walked in chronological order (same-date funding applied before same-date spending). The fund is shared across every custodian of the same petty cash (all their events are merged into one sequence); the balance must never go negative at any point in that sequence if the transaction's custodian has `controlNegativeBalance`. Because saved funding counts, editing (`PUT /payments/:id`) or deleting a DRAFT Payment that has TO_PETTY_CASH lines runs the same check (`assertPettyCashFundingChangeAllowed` in `routes/payments.ts`, using the service's `excludePaymentId`); unapprove doesn't change the balance so it has no check; approved re-edit keeps its delta check. Any future write path that affects this balance (new petty-cash transaction types, edits, reverts) must go through this service, not re-implement the sum. **Opening / year-close transfer:** `TreasuryOpeningPettyCash` (one row per petty cash, in the petty cash's own currency + base value; same `isSystemGenerated` rules as bank/cash rows) sets the balance at *period start − 1 day* (`openingAdjustments` in `pettyCashReviewService.ts`: the delta between the opening and the chain is injected as an event/an «افتتاحیه» ledger row with `custodianId = 0`; zero delta = nothing added, which is the normal case after a close). The chain is continuous across all fiscal years (`withoutFiscalPeriodScope`); edits dated inside a closed year are absorbed by the next opening's reset. Year-close section `PETTY_CASHES` (`computePettyCashClosing`) uses the *review* movements (approved funding − spendings) up to the period end, ignoring the next period's own opening; foreign-currency petty cashes get an amount-weighted funding `fxRate` as the base value (approximation — spending has no rate). Manual opening rows reject negative balances; system rows may be negative if the control was off.
- Purchase/sales invoices issue journal entries; purchase cost lines are unified/shared; receivable/payable accounts can be groupless; receipt types drive receipt settlement (موضوعات دریافت).
- Advance-receipt allocation to sales invoices (تخصیص پیش‌دریافت; spec `Documents/تخصیص پیش دریافت.md`): model `SalesInvoiceAdvanceAllocation` (invoice × `ReceiptSettlementLine` of a receipt type with nature ADVANCE_RECEIPT, amount in the invoice currency), logic in `services/salesInvoiceAdvanceService.ts`, endpoints `GET/PUT /sales-invoices/:id/advance-allocations` (permission `sales.operations.sales-invoices.allocateAdvance`), UI = «تخصیص پیش‌دریافت» action/dialog on the sales-invoice form. Candidates: same party, APPROVED receipt, date ≤ invoice date, same currency, allocatable > 0. Edit lock = registry `SALES_INVOICE_ADVANCE_LOCKS` (`{key, check(invoiceId)}`; add a new "circulation" by adding one entry — currently PAYMENT_FLOW [receipt/payment settlement lines referencing the invoice] and JOURNAL_ENTRY [invoice JE issued]). An allocated receipt can't be unapproved/re-edited (`assertReceiptAdvanceNotAllocated`), invoice edits must keep allocations valid (`assertAdvanceAllocationsStillValid`), and allocations reduce the receipt-picker remaining of the invoice. The invoice JE (`issue-journal-entry`) debits the advance account (the receipt type's account / `RECEIPT_SUBJECT` setting) at the receipt's historical rate and reduces the receivable by the allocated amount; the FX difference follows `getAdvanceReceiptMethodForDate(invoice.date)` (TRANSACTION_DATE_RATE → `FX_GAIN_LOSS` line; HISTORICAL_RATE → contra line on the first revenue account). Foreign-currency payable = invoice − allocated is never affected by rates. Two natures are allocatable (spec `Documents/تغییرات تخصیص پیش‌دریافت.md`): ADVANCE_RECEIPT (limit = invoice net amount, reduces the receivable-amount debit, revenue contra) and ADVANCE_VAT_RECEIPT (receipt-type nature «پیش دریافت ارزش افزوده»; limit = invoice VAT expressed in invoice currency = Σ vatAmount / fxRate, reduces the receivable-VAT debit, contra on the VAT credit account). The nature is stored on each allocation (`SalesInvoiceAdvanceAllocation.nature`, enum `AdvanceAllocationNature`), totals/limits/FX differences are kept separate per nature and never merged; all other rules (party, approved, date, currency, allocatable, payment-flow lock) apply to both. Receipt basis for nature ADVANCE_VAT_RECEIPT + PROFORMA_INVOICE (`candidatesForBasisType` in `routes/receipts.ts`, spec `Documents/مانده ارزش افزوده قابل دریافت پیش فاکتور.md`): remaining = quote VAT − VAT of invoices issued from the quote (invoice line → inventory line → `sourceSalesQuoteLineId`, or via order line → quote line; VAT ÷ invoice fxRate; no IsConverted flag, so partial/multi-step conversion works) − unallocated VAT advances (receipt amount minus its `SalesInvoiceAdvanceAllocation`s); the quote is offered only while remaining > 0 and new receipt amounts are capped by it. Receipt type nature SALES_VAT («ارزش افزوده فروش») on a SALES_INVOICE basis works the same way (`basisGroupOf` in `routes/receipts.ts`): limit = invoice VAT (Σ vatAmount ÷ fxRate), reduced only by VAT-group receipts and ADVANCE_VAT_RECEIPT allocations, so ordinary customer receipts never consume the VAT remaining and vice versa. Accounting-settings values are cached 60s in-process.
- Advance-payment allocation to purchase invoices (تخصیص پیش‌پرداخت; spec `Documents/تخصیص پیش‌پرداخت در فاکتور خرید.md`), the purchase mirror of the above — same shape, own independent procedure, plus a cost-basis effect the sales side has no equivalent of: model `PurchaseInvoiceAdvanceAllocation` (invoice × `PaymentSettlementLine` of a payment type with nature ADVANCE_PAYMENT, amount in invoice currency; single nature, no VAT split), logic in `services/purchaseInvoiceAdvanceService.ts`, endpoints `GET/PUT /purchase-invoices/:id/advance-allocations` (permission `supply-chain.operations.purchase-invoices.allocateAdvance`), UI = «تخصیص پیش‌پرداخت» action/dialog on the purchase-invoice form (DRAFT only). Candidates: same party, APPROVED payment, date ≤ invoice date, same currency, allocatable > 0. Edit lock = `PURCHASE_INVOICE_ADVANCE_LOCKS` (PAYMENT_FLOW [direct `PaymentSettlementLine.purchaseInvoiceId` rows — not the advance allocation itself], JOURNAL_ENTRY, and — unlike sales — APPROVED, since approval already consumes the allocations into `cost`/pricing; `assertPaymentAdvanceNotAllocated` blocks unapprove/re-edit of the source Payment, called from `routes/payments.ts`). Own dated procedure: `AccountingAdvancePaymentSetting`/`AdvancePaymentFxMethod` (`getAdvancePaymentMethodForDate`, AccountingSettings.tsx tab «تنظیمات ارز خرید» — never shares a record with the sales side's «تنظیمات ارز فروش» tab, same HISTORICAL_RATE/TRANSACTION_DATE_RATE values). Cost-basis effect (only for `basis=WAREHOUSE_RECEIPT` invoices, only under HISTORICAL_RATE, spec section «تأثیر تسعیر در قیمت تمام‌شده»): `PurchaseInvoiceLine` gets two system fields, `exchangeRateAdjustmentShare` and `cost` (= baseAmount + share; never shown/edited by the user), computed once at approval by `computePurchaseInvoiceLineCosts` (pro-rated by each line's net amount, largest-remainder rounding so the sum is exact) and reset back to `cost=baseAmount`/`share=0` on unapprove. **Both fields are in base currency** (explicit user decision) — the warehouse module has no currency concept at all (every other pricing write in it — `initialInventory.ts`, `warehouseAdjustments.ts`, `productionReceipts.ts`, `servicePurchaseInvoices.ts`'s own `INBOUND_RELATED_COST` — always writes a base-currency number), so approval's CROSS_ENTITY warehouse-receipt pricing (`routes/purchaseInvoices.ts`) now writes `cost` directly, no conversion. (Earlier revision had `cost` in invoice currency with a separate transient `costBase`; that dual representation was replaced by making `cost` itself base-currency everywhere, per explicit user decision — simpler than keeping two fields in sync. Before that, `cost` was invoice-currency and was mistakenly written straight into the warehouse's base-currency ledger for any foreign-currency `WAREHOUSE_RECEIPT` invoice — e.g. a $1,000 line priced inventory at 1,000 Rial instead of its ~40,000,000-Rial equivalent; fixed 1405/07/07.) The JE's own goods/INVENTORY debit line (`issue-journal-entry`) uses `cost` (base currency) directly when the INVENTORY account itself is base-currency (the common case); only when that account is itself currency-denominated does it convert back with `fromBaseCurrencyAmount(cost, fxRate, invoice.currency)` to debit that account in its own currency (`credit`/VAT amounts stay based on `amount`/`baseAmount`, unaffected — the payable owed to the supplier doesn't change). For TRANSACTION_DATE_RATE (any basis) or HISTORICAL_RATE on a `NO_BASIS` invoice (no receipt to absorb into), the diff is instead one extra JE line — `FX_GAIN_LOSS` (`debit = diff` when positive) for TRANSACTION_DATE_RATE, or a contra on the first goods debit account for HISTORICAL_RATE+NO_BASIS (`diff = histBase − atInvoiceBase` per allocation, summed; sign is chosen so the entry always balances). Verified end-to-end (including the WAREHOUSE_RECEIPT+HISTORICAL_RATE cost-absorption path itself, previously not exercised) with a real warehouse receipt + a temporary foreign currency + a directly-created advance payment: CROSS_ENTITY correctly holds the base-currency `cost`, and the full issued JE (inventory debit at the historically-locked base-currency cost, VAT debit at the current-rate base amount, payable/advance-consumption credits) balances exactly.
- Goods/service group type: `GoodsGroup.groupType` (enum `GoodsGroupType` PRODUCT | SERVICE) is stored **only on root groups** (`parentId = null`, required on create; children ignore it and inherit). `GET /goods-groups` adds `rootGroupType` to every group. Root type can't be changed while its subtree holds items of the other kind. `assertGroupMatchesKind` (routes/goodsItems.ts) rejects a GOODS item in a SERVICE-rooted group and vice-versa on create and on import; the shared item form (`GoodsItemShared.tsx`) only offers leaf groups whose `rootGroupType` matches the form (Goods ⇄ PRODUCT, Service ⇄ SERVICE). The migration backfills roots: SERVICE if the subtree has only services, else PRODUCT (mixed roots stay PRODUCT and can be fixed in the group form).
- Tax Affairs module («امور مالیاتی», registry module `tax-affairs` › settings › form `tax-memories`, route `/tax-memories`): first form = «حافظه مالیاتی» (`TaxMemory`; fields Persian/English company name, national id, country `IR`, email, `taxMemoryUniqueId` — entered manually after the Taxpayer System issues it). First save generates an RSA-2048 pair (`services/taxMemoryService.ts`): public key (SPKI PEM `BEGIN PUBLIC KEY`) and PKCS#10 CSR (SHA-256, subject C=IR, O/CN = English name, OU = Persian name (UTF-8), serialNumber = national id, emailAddress) from the **same** pair via `node-forge`; downloads `GET /tax-memories/:id/public-key` → `public-key.txt`, `/csr` → `csr.txt` (permissions `downloadPublicKey`/`downloadCsr`). The private key is stored only AES-256-GCM-encrypted (`privateKeyEncrypted`, key = scrypt of `TAX_KEY_ENCRYPTION_SECRET`, falling back to `JWT_SECRET` — **changing that secret makes stored keys undecryptable**); every response goes through `serialize()` (whitelist), no endpoint returns key material, nothing key-related is logged. Server rejects any `countryId` ≠ IR and any attempt to send public key/CSR/private key; editing company info re-signs a new CSR with the stored key (public key never changes). Out of scope for now: invoice submission/inquiry, JWT/JWS/JWE, API integration, Commercial Books.
- Numbering patterns («الگوی شماره‌گذاری», registry `settings.operations.numbering-patterns`, route `/numbering-patterns`): `NumberingPattern` (title, hasTaxMemory + taxMemoryId — required iff hasTaxMemory, must be empty otherwise —, resetPerFiscalYear, restrictEarlierDates, lastNumber) **owns the sequence** (the tax memory does not); items `NumberingPatternItem` = form (`SALES_INVOICE` | `SALES_RETURN`) + salesType + salesCenter, **globally unique** (DB unique + server message naming the clashing pattern); all items of a pattern share one counter. Allocation (`services/numberingPatternService.ts`, `allocateDocumentNumber`) is a single atomic `INSERT … ON CONFLICT (patternId, scopeKey) DO UPDATE SET lastNumber = lastNumber + 1 RETURNING` on `NumberingPatternCounter` (scopeKey = fiscalPeriodId when `resetPerFiscalYear`, else 0) **inside the same interactive transaction that creates the document** (routes/salesInvoices.ts, salesReturnInvoices.ts POST) — row lock serialises concurrent creators, rollback frees the number (no gaps), plus unique index (numberingPatternId, fiscalPeriodId, number) on both document tables; tested with 40 parallel creates (unique + contiguous). `lastNumber` = migration seed: next number = lastNumber + 1; with reset it seeds only `seedFiscalPeriodId` (fiscal year current when the pattern was created), other years start at 1. Date rule: after taking the counter lock, new document date must be ≥ MAX(date) of documents numbered by the pattern (scoped to the fiscal year when resetting); on edit only when the date changed, excluding the document itself. Documents keep their number on edit; edit is rejected if it would move the document to another pattern or (with reset) another fiscal year. **Saving a Sales Invoice / Sales Return (create and edit) is rejected when no pattern matches its (form, sales type, sales center): «برای این مرکز و نوع فروش، الگوی شماره‌گذاری تعریف نشده است.»** (`NO_PATTERN_MESSAGE`; the legacy «max + 1» numbering was removed). Documents store `numberingPatternId`; pre-existing documents have `NULL` (their old numbers are kept — a legacy document whose combination now has a pattern keeps its number on edit) and stay protected by a **partial unique index** (`…_legacy_number_key`, raw SQL in the migration — Prisma can't model it, so `migrate diff` will list it). Once a pattern has documents its lastNumber / reset flag / used items are locked and it can't be deleted. Out of scope this phase: store sales, store sales return, contractor progress statements and any other document type.
- Sales invoice — **basis per line** (not in the header): `SalesInvoiceLine.basis` (`SalesInvoiceLineBasis`: NO_BASIS | SALES_DELIVERY (حواله فروش) | SALES_ORDER | SALES_QUOTE (پیش‌فاکتور)) is the single source of truth; `SalesInvoice.basis` was dropped (migration `20261019100000_sales_invoice_line_basis` copies each invoice's old header basis to all its lines first — NO_BASIS→NO_BASIS, SALES_DELIVERY→SALES_DELIVERY — keeping `sourceInventoryLineId` and all other data). Source columns on the line: `sourceInventoryLineId` (delivery line, as before), new `sourceSalesOrderLineId`, `sourceSalesQuoteLineId`; only the one matching the line's basis may be set. One invoice → one unified grid → each row picks its basis first. `validateLines` (routes/salesInvoices.ts) enforces everything server-side: NO_BASIS lines = **services only** (legacy goods NO_BASIS lines already on that invoice are grandfathered on edit); for any basis document: party = header customer, sales center/type/currency = header's, basis date ≤ header date, order/quote must be APPROVED; a **Warehouse Issue** has no center/type/currency of its own — party (via `InventoryDocument.detailCode`) and date are always checked, and center/type/currency only when its lines come from an order/quote (taken from that base). Remaining quantities: order/quote lines also subtract invoice lines that reference them directly (`salesOrderLineUninvoiced` / `salesQuoteLineUninvoiced`; quote also subtracts quantity already ordered); price of order/quote lines (and deliveries based on them) is recalled from the base and locked. **Order/Quote lines = services only**: Sales Order and Proforma (like No Basis) offer/accept only SERVICE lines — goods enter an invoice only through a Warehouse Issue (server rejects goods lines for these bases; legacy goods lines already on that invoice are grandfathered on edit); remaining = line qty − invoiced (− quantity already ordered, for quotes), only lines with remaining > 0 are listed. Selector API (**line level**, single endpoint): `GET /sales-invoices/basis-lines?type=SALES_DELIVERY|SALES_ORDER|SALES_QUOTE&customerId&salesTypeId&salesCenterId&currencyId&date[&excludeInvoiceId]` → billable lines (remaining > 0) of header-compatible documents only (incompatible documents are never listed; save re-validates). A delivery's base info (currency/sales type/base amount) is used server-side only to compute price/amount and is NOT shown in the selector. Frontend: per-row basis `<select>`; for a sourced basis the row has a **line-level** `RecordPickerField` (multi-select, columns number / item / remaining; remaining is live-reduced by the other rows referencing the same source line) that fills the row (+ new rows for extra ticked lines); the item picker keeps its single-select behaviour (services only for NO_BASIS). Edit/load reads each line's basis and source (`source` object in the detail) — never from the header. The old Additional-Items-tab design (PR #34) was dropped.
- **Receipt/Payment type account (معین) lives only in «تعیین حسابهای معین»** (`TreasuryAccountSetting` RECEIPT_SUBJECT / PAYMENT_SUBJECT, per type; migration `20261021100000_remove_type_account` copied each NONE-basis type's old `accountId` there and dropped `ReceiptType.accountId`/`PaymentType.accountId`). Receipt/payment/petty-cash-summary/purchase-advance/sales-advance journals resolve it from that setting for every basis that doesn't take it from an invoice (NONE, order, …); invoice-basis types still take the payable/receivable account from the invoice's accounting settings. A missing setting blocks issuing with a message pointing to that form. The type forms have no معین field.
- Purchase **advance VAT** («پیش‌پرداخت ارزش افزوده», `PaymentNature.ADVANCE_VAT_PAYMENT`, basis NONE only; migration `20261020100000_purchase_advance_vat`): `PurchaseInvoiceAdvanceAllocation`/`ServicePurchaseInvoiceAdvanceAllocation` carry `nature` (`PurchaseAdvanceAllocationNature` ADVANCE_PAYMENT | ADVANCE_VAT_PAYMENT, default ADVANCE_PAYMENT). `services/purchaseInvoiceAdvanceService.ts` mirrors the sales service: principal advances cap at the invoice net total, VAT advances cap at the invoice VAT (`purchaseInvoiceVatTotal` = (line + other-cost-line VAT)/fxRate), each checked separately; the dialog shows both. Both invoice journals reduce the single payable credit by all allocations, credit each advance's own account, and book FX difference per nature (VAT diff → FX gain/loss, or the VAT debit account under the historical-rate method); line-cost FX share (`computePurchaseInvoiceLineCosts`) uses principal advances only; list `advanceAmount` = principal only. Payment-selector remaining for a purchase invoice (`paymentBasisCandidates.ts`, per group): principal = invoice amount − ADVANCE_PAYMENT allocations − approved/petty-cash non-VAT payments; VAT (PURCHASE_VAT) = invoice VAT − ADVANCE_VAT_PAYMENT allocations − approved/petty-cash PURCHASE_VAT payments. A fully pre-paid invoice drops out of the selector and save is rejected.
- Advance-payment allocation on the **service purchase invoice** (same feature, reused): the allocation logic in `services/purchaseInvoiceAdvanceService.ts` is parameterised by `PurchaseAdvanceKind` (`GOODS` | `SERVICE`, default GOODS so goods callers are unchanged); SERVICE uses model `ServicePurchaseInvoiceAdvanceAllocation`, endpoints `GET/PUT /service-purchase-invoices/:id/advance-allocations` (permission `…service-purchase-invoices.allocateAdvance`), net total = Σ(amount − discount) of the invoice's `PurchaseCostLine`s, same candidate rules/locks (PAYMENT_FLOW applies to GOODS only). A payment advance line is one shared pool: allocatable = amount − allocations to *any* invoice of either kind (`splitAllocations`), and `assertPaymentAdvanceNotAllocated` checks both tables. Service JE (`issue-journal-entry`): credits the advance account at the historical value and reduces the payable credit (no cost-share mechanism exists for service lines); the FX diff goes to `FX_GAIN_LOSS` (TRANSACTION_DATE_RATE, or HISTORICAL_RATE when the invoice has no «هزینه» line) or onto the first «هزینه» debit line (HISTORICAL_RATE). Frontend: the dialog is the shared component `components/PurchaseAdvanceAllocationDialog.tsx` (prop `basePath`) used by both `PurchaseInvoices.tsx` and `ServicePurchaseInvoices.tsx`; any future invoice form implementing the same `GET/PUT {basePath}/:id/advance-allocations` contract only passes its `basePath`. The service-invoice list has a «پیش‌پرداخت» column.

- Service accounting treatment & «خرید خدمت» (`GoodsItem.accountingTreatment`, enum `ServiceAccountingTreatment` = `EXPENSE` «هزینه» | `INVENTORY_COST` «بهای موجودی», only for `kind=SERVICE`, null for goods; shown in the service form's «حسابداری خدمت» tab; default EXPENSE; excel import column «نحوه حسابداری»; rule module `services/serviceAccountingTreatment.ts`). Applies to every `PurchaseCostLine` — service purchase invoice lines **and** the «سایر هزینه‌ها» tab of the goods purchase invoice: the line basis is derived from the service, never chosen freely. **INVENTORY_COST ⇒ basis WAREHOUSE_RECEIPT and a receipt is mandatory; EXPENSE ⇒ NO_BASIS and any receipt/allocations are rejected** (server: `resolveCostLineBasis` in both `validateLines`/`validateOtherCostLines`, errors, not silent fixes; frontend: picking a service sets and locks the basis select, clears the receipt for expense, and blocks save with the same messages). Debit accounts at journal issue: EXPENSE ⇒ the new accounting-settings type `SERVICE_PURCHASE` («خرید خدمت», `GoodsServiceAccountingSetting.serviceId`, keyed by the service only — no accounting group/purchase type; created in «حسابداری کالا و خدمت», only EXPENSE services are selectable and the API rejects INVENTORY_COST/non-service/duplicate) — `PURCHASE_CONTROL` is no longer used for services (still used for goods); INVENTORY_COST ⇒ no purchase account exists for the service; the debit is the `INVENTORY` account of each allocated receipt line (goods accounting group + the receipt's warehouse group) so the user never picks it. `PURCHASE_PAYABLE` and `PURCHASE_VAT` (keyed by the service's accounting group) are unchanged, and service sales keep the accounting-group structure (`SALES_REVENUE` etc.: many services share a group's account). Guards: changing a service's treatment is refused once it is used in a purchase line, and to INVENTORY_COST while it has a `SERVICE_PURCHASE` setting; a service with a setting can't be deleted. Migrations `20261012100000` (enum value) + `20261012100100` (column, `serviceId`, first data pass, and a `SERVICE_PURCHASE` setting per EXPENSE service when its group's `PURCHASE_CONTROL` rows all point to one account, otherwise define them by hand) + `20261012100200` (final, exact initialisation of every existing service's treatment from history: INVENTORY_COST if the service has ever been on a **service purchase invoice** line (`PurchaseCostLine.servicePurchaseInvoiceId` not null) with basis/receipt `WAREHOUSE_RECEIPT`, else EXPENSE; it only writes `GoodsItem.accountingTreatment` of services — invoices, vouchers, receipts, allocations and settings are untouched, verified by table fingerprints — and is idempotent; receipts used only in a goods purchase invoice's «سایر هزینه‌ها» deliberately don't count, so such a service becomes EXPENSE and its old receipt-linked cost line must be re-saved without the receipt before its journal can be issued).
- Opening Operations (`TreasuryOpening.isSystemGenerated`, migration `20261013100000`; `routes/treasuryOpenings.ts`, `pages/TreasuryOpenings.tsx`): an opening is either **system-generated** (created by the previous fiscal year's Period-End close via `ensureOpening`) or **manual** (initial deployment). System-generated openings are wholly read-only: `PUT`/`DELETE` are rejected on the server (`SYSTEM_LOCK_MESSAGE`, regardless of the payload — no edit, no add/delete/modify of any item in any of the four tabs); the form disables every control (tabs stay clickable to view), disables save, hides delete and shows a banner; they are created/changed/removed only by close/reopen in the previous year (`reopenSection`). Manual rule: at most **one** manual opening in the whole system, and it can be created only while **no** system-generated opening exists (`manualCreationBlockedReason`, enforced in `POST`, exposed by `GET /treasury-openings/creation-status` so the list disables «جدید» with the reason and the new form is locked). A close refuses to write into an existing manual opening of the target year (delete it first). Migration backfill: an opening is flagged system-generated when it has system rows/transferred cheques or the previous period has closes (a legacy opening that mixed manual and system rows becomes fully read-only); existing manual openings beyond one are not touched, they just block further manual creation. The openings list is fiscal-year scoped as before, so a system opening of the next year appears when that year is selected.
- Grid «Best Fit» button (`lib/bestFit.ts`, `components/BestFitIcon.tsx`): a toolbar icon on `DataTable` (every list page, in the header toolbar next to export/print) and `SelectableBalanceTable` (review reports, in the tabs bar). Purely client-side and display-only: it measures an invisible clone of the rendered table (nowrap, auto layout) so each column becomes as wide as its widest header/cell on the **current page**, then sets fixed widths in component state (`table-layout: fixed`). Nothing is stored (no backend call, no localStorage, no change to column `width` defaults or grid config), and the widths reset whenever the page, page size or displayed rows change. The totals row under a grid re-measures the header so it stays aligned. By explicit decision it is **not** applied to the editable form line grids (journal entries, invoices, …): those have their own locking rules (a locked entry disables every button in its toolbar) and hand-built toolbars.
- Form Type (`lib/formTypes.ts`, `NavItem.type` in `navConfig.ts`): every menu item has a central **form type** that defines its common behavior — `list` (list + new/edit forms: the right-side menu shows the **List (folder) icon** next to the form and the label opens the «new» form), `operational` (a single page that is itself the operation — closing, confirmations, pricing, settings, tree forms — **no List icon**) and `report` (review/report pages — **no List icon**). The type is inferred when omitted (an item with `create` = list, without = operational); **reports must set `type: "report"` explicitly**. The behavior is resolved in one place (`resolveNavBehavior` / `FORM_TYPE_BEHAVIOR`) and rendered by the single `NavItemRow` in `Layout.tsx` (shared by the normal and the collapsed-flyout menus) — never hide the folder icon per form; to add behavior common to a type (or a new type), extend `FORM_TYPE_BEHAVIOR` and read it via `resolveNavBehavior`. New form checklist: add the item to `navConfig.ts`; give `create` for list forms, `type: "report"` for reports, nothing for operational forms.

## Versioning & releases

- The system has one release version (semver `major.minor.patch`), first set to **1.0.0**. It lives in four files that must always match — `backend/package.json` (the source of truth the API reads), `backend/package-lock.json`, `frontend/package.json`, `frontend/package-lock.json` — and is changed **only** by `node scripts/release.mjs patch|minor|major|x.y.z` (never edit those fields by hand). `node scripts/release.mjs --check` verifies the four files agree and that `CHANGELOG.md` has the current version (run it before tagging/building).
- Choosing the number: **patch** = bug fixes only; **minor** = new backward-compatible features (including additive migrations); **major** = breaking change or a manual migration step for the operator.
- Every change that matters to users/operators is written under `## [Unreleased]` in `CHANGELOG.md` **in the same PR that makes it**. A release = the script (it names the Unreleased section with the version and date, opens a fresh empty one, and refuses to run when Unreleased is empty) → `git commit -m "Release vX.Y.Z"` → `git tag vX.Y.Z` → build the Docker images tagged with the version (`…/accounting-erp-backend:X.Y.Z` and `:latest`, same for frontend).
- The About dialog (top bar, next to user settings; `components/AboutModal.tsx`, `routes/about.ts`, `GET /api/about`) shows «نسخه» (the release version) and «پایگاه داده» = the **schema version**: the newest Prisma migration applied on that database (`_prisma_migrations`, its 14-digit timestamp + name), with the PostgreSQL version and the number of applied migrations. It warns when the newest migration bundled with the running app is not yet applied (`database.upToDate === false`) and when the frontend's own version (`__APP_VERSION__`, injected from `frontend/package.json` by `vite.config.ts`) differs from the server's.

## Working rules for this repo

- Match existing patterns: new route file + register in `index.ts` + `authz/registry.ts` + `navConfig.ts` + `App.tsx` + page; schema change ⇒ Prisma migration.
- Reuse `journalEntryService`, `assertRecordNotStale`, fiscal scoping, and shared components instead of re-implementing.
- Don't commit `dist/`, `~$` temp files, or `.env`.
- User-visible changes get a line under `## [Unreleased]` in `CHANGELOG.md` in the same PR; versions are bumped only with `scripts/release.mjs` (see «Versioning & releases»).
