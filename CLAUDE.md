# Accounting ERP — Project Memory

Persian (RTL, Jalali calendar) web accounting/ERP for small–medium businesses. Monorepo: `backend/` (Express + Prisma + PostgreSQL) and `frontend/` (React SPA). UI text, comments, error messages and design docs are in **Persian** — keep new user-facing text and code comments in Persian, consistent with the surrounding code.

Last refreshed: 2026-09-20 (branch `master`; main branch for PRs is `main`).

## Stack & run

- Backend: Node + Express 4 + TypeScript, Prisma 5, PostgreSQL 16, JWT (`jsonwebtoken`, `bcryptjs`), `zod`, `express-async-errors`. Port 4000, all routes under `/api`.
- Frontend: React 18 + TS + Vite 5, `react-router-dom` 6, `react-multi-date-picker` (Jalali), `recharts`, `xlsx`. No UI kit — hand-written components and one `styles.css`. Dev port 5173 (Docker maps 5174).
- Docker: `docker compose up --build` (db on host 5433, backend 4000, frontend 5174; source bind-mounted, watch mode). Frontend derives API URL from `window.location.hostname` unless `VITE_API_URL` is set.
- Backend scripts: `npm run dev` (tsx watch), `build` (tsc), `seed`, `prisma:migrate`, plus maintenance scripts in `backend/src/scripts/` (cleanup-orphans, recompute-has-transactions, goods backfill/backup/restore/delete).
- Frontend: `npm run dev`, `npm run build` (`tsc -b && vite build`). `backend/dist` and `frontend/dist` are untracked build output.
- Default seed login: mobile `0999999999`, password `Admin@123`.
- No test suite exists; verify with `tsc` builds and by using the feature in the browser.
- Migrations: `backend/prisma/migrations/` (~70, timestamped `2026MMDD...`). Schema is `backend/prisma/schema.prisma` (~3000 lines, ~134 models, ~55 enums). Add a new migration for every schema change.

## Backend layout (`backend/src`)

- `index.ts`: registers ~79 route files. Order: public `/api/auth` → `requireAuth` → `fiscalScopeContext` → everything else. Global error middleware at the end.
- `routes/`: one file per form/group; call Prisma directly (no repository layer). Shared business logic lives in `services/` (`journalEntryService` = the single entry point for issuing journal entries, `goodsPricingService`, `warehouseMovementService`, `warehouseStockService`, `warehouseConfirmationService`, `serialLifecycleService`, `batchService`, `documentEffectsService`, `salesReviewService`, `importJobService`, …).
- `utils/`: pure helpers (`coding.ts` auto detail codes, `concurrency.ts`, `currencyConversion.ts`, `vatCalculation.ts`, `jalaliDate.ts`, `tableFilters.ts`, `warehouseTracking.ts`, …).
- `authz/`: RBAC. `registry.ts` is the **single source of truth** for modules/forms/actions (base actions view/create/edit/delete + custom). Routes use `can("module.sub.form.action")` from `guard.ts`; an unregistered key crashes the server at boot. `sync.ts` syncs the registry to DB; the admin permission tree comes from `GET /api/authz/tree`. To add a form/action, edit `registry.ts` (and `navConfig.ts` for menu).
- `middleware/fiscalScope.ts` + `lib/prisma.ts`: frontend sends `x-fiscal-period-id`; the Prisma client wrapper **automatically scopes list queries** of every model having `fiscalPeriodId` to the current fiscal period (fallback: latest period). `bypassFiscalScope` exists in request context for exceptions. Dates of documents must fall in the current fiscal period (`utils/fiscalPeriodValidation.ts`).
- `utils/concurrency.ts`: lost-update protection — GET/:id returns `updatedAt`; PUT/:id calls `assertRecordNotStale(existing.updatedAt, req.body.updatedAt, label)` right after the not-found check. Frontend `lib/api.ts` remembers and re-sends it automatically.
- `importProcessors/` + `ImportJob`: async Excel import per record type.
- `lib/bulkError.ts`: structured bulk-failure errors (`details`) rendered by frontend `BulkErrorDialog`.
- `data/warehouseDocNatureMatrix.ts`: warehouse document nature rules.

## Frontend layout (`frontend/src`)

- `App.tsx` routes (list/new/edit per form), `navConfig.ts` menu, `pages/` (~95 files, one per form/report), `components/` shared (DataTable, Modal, FormPage, TreeView, RecordPicker, JalaliDatePicker, AmountInput, FxAmountDialog, Wizard, TabsBar, …), `lib/` (api, AuthContext, TabsContext, `useCrud`, `useDocumentForm`, `usePermissions`, formatters, review-report caches, `currencyConversion`, `vatCalculation`, `costAllocation`).
- Server is the source of truth; frontend only does display-side helper calculations.
- Submodule order (general rule, all modules): «تنظیمات» first, operations/other groups in their defined order in the middle, «گزارش…» last. Enforced centrally — `MODULES` in `frontend/src/navConfig.ts` and `sortSubModules` in `backend/src/authz/registry.ts` (permission tree) — so the definition order in those arrays doesn't matter; new submodules just need the right title.
- Keyboard (shared components): every selector dialog (`RecordPicker`, `MultiRecordPicker`, hook `components/pickerKeyboard.ts`) supports ↑/↓ (PageUp/PageDown) to move the highlighted row, Enter to select it (multi-select: Enter ticks, Ctrl+Enter confirms), Esc to close; the first filter box is auto-focused so "type a filter, press Enter" picks the first match. `FormPage` binds Ctrl+S/Cmd+S to the toolbar Save button (skipped while a dialog is open or when Save is disabled). New selectors/forms should reuse these components rather than re-implementing keys.
- Delete from an edit form (base, `components/FormPage.tsx#handleDelete`): after a successful `onDelete` (detected by the page having navigated away from the form path) the form's tab is closed with `closeTab(id, { preferPath: closePath })` — go to the form's list tab if it is open, otherwise the neighbor tab / home — instead of letting the page's own `navigate(list)` turn the tab into the list. Pages keep their own `navigate` after delete; no per-page change.
- Description defaults in Payment/Receipt forms: a new instrument row starts with the header description (on new documents, typing the header description also updates instrument rows that still hold the default); loading an instrument into the subjects grid copies its description to the subject row. Payment subject amount defaults from the instrument's remaining amount for no-basis types.
- Sales delivery (حواله فروش) basis: NO_BASIS / SALES_ORDER / SALES_QUOTE (پیش‌فاکتور). Quote-based lines store `InventoryDocumentLine.sourceSalesQuoteLineId` (enum `InventoryBasis.SALES_QUOTE`); a quote line's deliverable remaining = quantity − quantity converted to sales orders − quantity delivered directly; the sales-order quote picker also subtracts direct deliveries, and a quote with direct deliveries can't be unapproved. The quote's customer must match the header party's customer.
- Sales invoice price call-through from the delivery's base document (فراخوانی قیمت در فاکتور; spec `Documents/فراخوانی قیمت در فاکتور.md`): for a `SALES_DELIVERY`-basis invoice line whose source delivery line was itself issued on `SALES_ORDER`/`SALES_QUOTE` basis (`InventoryDocumentLine.sourceSalesOrderLineId`/`sourceSalesQuoteLineId`), `unitPrice`/`amount` are no longer user-entered — `routes/salesInvoices.ts#validateLines` always recomputes and overwrites them (ignoring whatever the client sent), on both create and edit. `salesOrderLineUninvoiced`/`salesQuoteLineUninvoiced` (mirroring `salesDeliveries.ts`'s own `salesOrderLineRemaining`/`salesQuoteLineRemaining`, but summing *invoiced* qty/amount — via each delivery line's `salesInvoiceLines`, across every delivery drawn from that order/quote line — instead of *delivered*) give the order/quote line's uninvoiced remaining; `deliveryLineBaseInfo` picks whichever of the two the delivery line actually used and returns it with the order/quote's own currency/salesType. **Delivery-based formula (amount first, then price; supersedes the old «price rounded to 4 decimals × qty»)**: `amount = round(uninvoicedAmount ÷ uninvoicedQuantity × qty, invoice-currency decimals)`, then `unitPrice = round(amount ÷ qty, 10)` — always 10 decimals for the price, currency decimals for the amount (the invoice currency equals the base order/quote currency, enforced); `discount = round(uninvoicedDiscount ÷ uninvoicedQuantity × qty, currency decimals)`. The uninvoiced triple (computed once per distinct order/quote line per save and reused across every invoice row referencing it, even via different delivery lines) is also sent to the form (`baseUninvoicedAmount/Discount/Quantity` in `basis-lines`, `source.baseUninvoiced` in the detail) so `SalesInvoices.tsx` (`deliveryPrice`, rows' `baseUninv*`) mirrors the server exactly, live on quantity change. **All three bases use this one formula** (`priceFromBase` in `routes/salesInvoices.ts` — the single implementation used by `validateLines` and the picker; `SalesInvoices.tsx#deliveryPrice` mirrors it): the base triple is the uninvoiced amount/discount/quantity of the order/quote line for delivery- and order-based rows, but the **whole line** (total amount/discount/quantity) for a direct quote-based service row (unchanged semantics: a quote line may be partly converted to orders), so partial direct-quote invoices can leave a rounding remainder of the quote amount. The invoice's header currency and salesType must equal the base document's (rejected otherwise — a delivery has neither field itself). A NO_BASIS delivery (no order/quote behind it) is untouched — price stays user-entered, exactly as before. This is a DB-derived lock, not a flag: nothing new is stored on `SalesInvoiceLine`, since the source delivery line's own `sourceSalesOrderLineId`/`sourceSalesQuoteLineId` (persisted at delivery-creation time) is re-read and reapplied on every save, including edits. `GET /sales-invoices/pickable-sales-delivery-lines` returns a `base` field (currency/salesType titles+ids, base amount/quantity, uninvoiced amount/quantity, `null` for NO_BASIS deliveries) so the picker can show it; `SalesInvoices.tsx`'s picker columns display it and the fی/مبلغ (`unitPrice`/`amount`) `AmountInput`s are `disabled` (with an explanatory `title`) whenever the picked row has a `base` — purely a UX mirror of the server-side lock, computed live from `pickableLines`, not a stored row flag.
- **Line discount on quote / sales order** (`SalesQuoteLine.discount` / `SalesOrderLine.discount`, amount in the document currency, default 0; migration `20261025100000`): VAT of these lines is on `amount − discount` (like the invoice); lists show the net total (`مبلغ کل (پس از تخفیف)`); receipts' order/quote basis total (`totalOf` in `routes/receipts.ts`) is net too. Order-from-quote lines take `discount = (quote line discount ÷ quote qty) × qty` and ignore client input (locked in the UI like the price). **Invoice discount call-through = the same «remaining ÷ remaining × qty» formula as the price**, mirrored branch by branch in `routes/salesInvoices.ts#validateLines`: SALES_DELIVERY from an order/quote → `base.uninvoicedDiscount ÷ uninvoicedQuantity`; SALES_ORDER → `remainingDiscount ÷ remainingQty`; SALES_QUOTE → `totalDiscount ÷ totalQty` (same as that branch's price); each rounded to 4 decimals per unit then × qty, `computedDiscount` overrides the client's `discount` (NO_BASIS lines keep the user's discount). `salesOrderLineUninvoiced`/`salesQuoteLineUninvoiced` return `totalDiscount`/`remainingDiscount` (line discount − discount of invoice lines already drawn from it, directly or via deliveries); the basis picker rows carry `unitDiscount`; `SalesInvoices.tsx` disables the discount input on `priceLocked` rows and recomputes it with the quantity. Because the last invoice takes the whole remaining qty, (remaining ÷ remaining) × remaining returns exactly the remaining discount — no rounding-remainder logic is needed.
- Sales invoice void action (ابطال؛ scoped to SalesInvoice only, per explicit user decision — no other invoice-like document has this yet): `POST /sales-invoices/:id/void` (permission `sales.operations.sales-invoices.void`) is a plain status flip to `VOIDED` (new value on the shared `SalesDocStatus` enum — SalesQuote/SalesOrder/SalesReturnInvoice share the enum but no code writes `VOIDED` on them) — no mirror/reversal document, no separate voiding process, matching the explicit spec. Allowed only when the invoice has neither an issued journal entry (`journalEntryId`) nor any row referencing it as a transaction — checked by counting `ReceiptSettlementLine`/`PaymentSettlementLine`/`SalesInvoiceAdvanceAllocation`/`PettyCashPayment`/`PettyCashSummaryLine` rows with this `salesInvoiceId` (there's no existing combined helper for this; the four other invoice-like documents — PurchaseInvoice/ServicePurchaseInvoice/SalesReturnInvoice — only guard delete on `journalEntryId`, so this check was written from scratch here and isn't shared). Once voided, the invoice is fully locked: edit/delete/`issue-journal-entry` all reject with `status === "VOIDED"` guards, and `SALES_INVOICE_ADVANCE_LOCKS` (`services/salesInvoiceAdvanceService.ts`) gained a `VOIDED` entry so advance-allocation edits reject too (same extensible-array pattern as `PAYMENT_FLOW`/`JOURNAL_ENTRY`). Frontend (`SalesInvoices.tsx`): `locked` now also covers `status === "VOIDED"` (fieldset + save disabled, same as the journal-entry lock); the «ابطال» button (`VoidIcon`, same shape as `ChequeBookLeaves.tsx`'s) sits next to «صدور سند حسابداری» (only shown pre-JE, pre-void) with a `window.confirm`; the list and the edit-form header both show a «وضعیت» column/field (`SALES_INVOICE_STATUS_FA`). Two additional consumer-side exclusions per spec: `services/salesReviewService.ts#getSaleLines` filters `salesInvoice.status: { not: "VOIDED" }` (Sales Review has no other status filtering — SalesInvoice.status was otherwise a dead field, since this invoice never had an approve step); and the two SALES_INVOICE basis-candidate sources that feed "the shared invoice selector" — `services/paymentBasisCandidates.ts` (Payments/PettyCashPayments) and `routes/receipts.ts`'s own local `candidatesForBasisType` (Receipts) — both default-exclude `status: "VOIDED"` with an `includeVoided` opt-in parameter (per spec: "exceptions explicitly configured at the relevant usage," currently unused by any caller). **Voided invoices never count as «invoiced»**: every «uninvoiced remaining» computation of a delivery line, sales-order line and quote line (quantity, amount, discount — `salesDeliveryLineRemaining`, `salesOrderLineUninvoiced`, `salesQuoteLineUninvoiced`, the delivery doc loader and the basis-lines picker) goes through the single `ACTIVE_INVOICE_LINES` filter (`salesInvoice.status != VOIDED`) in `routes/salesInvoices.ts`, as does the proforma remaining in `routes/receipts.ts` — a delivery of 100 with a voided invoice of 100 still has 100 uninvoiced. There is no single centralized "Invoice Selector" component/endpoint in this codebase (`RecordPickerField` is a generic UI shell reused per-site; each site owns its own backend candidate query) — a future invoice type needing the same exclusion must add its own `status`-filter at its own candidate source(s), same as these two.
- Accounting procedures & settings (`Documents/رویه ها و تنظیمات حسابداری.md`; menu حسابداری › تنظیمات › «رویه‌ها و تنظیمات حسابداری», route `/accounting-settings`, permission form `accounting.settings.accounting-settings.*`): a tabbed page (tabs: تنظیمات ارز, ارزش افزوده; add a tab = new entry in `TABS` + a `DatedSettingConfig` in `pages/AccountingSettings.tsx`). All settings are date-based — each record has a unique start date and the effective value for a date is the latest record with startDate ≤ that date (`services/accountingSettingsService.ts`: `getVatRatePercentForDate`, `getAdvanceReceiptMethodForDate`, cached 60s, invalidated on writes). VAT engine: `resolveVatRatePercent(goodsItem, defaultRatePercent)` no longer has a fixed 10% — every VAT-computing validator (purchase/service-purchase/sales/sales-return invoices, quotes, orders) receives the document date and passes `await getVatRatePercentForDate(docDate)` (a special item's own rate still wins); frontend forms use `useVatRates()`/`vatRateForDate` for live display only. A migration seeds one initial 10% record (2000-01-01) so existing behavior is unchanged; at least one VAT record must always exist and a date with no record raises an error. The advance-receipt FX recognition method (`AdvanceReceiptFxMethod`) is consumed by the sales-invoice advance allocation journal entry (see Domain conventions).
- Fiscal-year date fields (base behavior): every document-date `JalaliDatePicker` gets the prop `fiscalYear` — it limits the calendar to the user's selected fiscal period (`minDate`/`maxDate`, days outside disabled; manually typed out-of-range dates get a red border + tooltip) via `lib/useSelectedFiscalPeriod.ts` (one shared cached `/fiscal-periods` fetch). New document forms just add `fiscalYear` to their date picker. Backend enforcement is the truth: `assertWithinCurrentFiscalPeriod(periodId)` / `assertDateWithinCurrentFiscalPeriod(date)` in `utils/fiscalPeriodValidation.ts` (message includes the period range); use one of them in every route that accepts a document date.
- Default currency (base rule): every «ارز» field of a new document defaults to the base currency. Header currency selects use the hook `lib/useDefaultBaseCurrency.ts` (`enabled: !editId && loaded`, fills only an empty value, never overwrites the user's choice or an existing document); Receipts/Payments give new CASH instrument rows the base currency (bank-transfer rows take their bank account's currency, cheques are always base); journal-entry lines and treasury-opening cash rows already start on base. A new form with a currency select must use the hook.
- Multiple new forms at once (base behavior, `lib/TabsContext.tsx` + `lib/usePersistedState.ts`): opening a `/new` form whose path is already open in a tab creates another tab with the unique path `…/new?_i=<n>` instead of jumping to the existing one; `usePersistedState`/`hasPersistedState` transparently rewrite `form:<pathname>…` keys to `form:<pathname>@<n>…` for such tabs so each keeps independent state, and `clearFormState` clears only that instance. `/edit` forms stay one tab per record. Pages need no changes.
- Cheque document reviews («مرور اسناد دریافتنی/پرداختنی», treasury › گزارش; spec `Documents/تغییرات نقدینگی و چک راه اندازی مرور اسناد دریافتی و پرداختی.md`): one page `pages/ChequeDocumentsReview.tsx` (prop `kind`), routes `routes/chequeReview.ts` (`/cheque-review/:kind/statuses|cheques|details`), data `services/chequeReviewService.ts` — no duplicated data: events are read from approved receipts/payments/deposits/deposit-returns/clearings (+ opening) of each `ChequeItem`; a cheque is listed if any of its events falls in the range; the range must lie inside ONE fiscal period (`assertSingleFiscalPeriod`, also checked in the page). Chained tabs وضعیت ← اسناد ← جزئیات. Receipt cheque instrument rows require a cash box (`cashBoxId`, validated in `cleanOneInstrumentLine`; cash review still counts CASH rows only).
- Base grids always show their column headers, also when empty or loading (`DataTable`, `SelectableBalanceTable` render the message inside the table body). Note: the automatic «شماره سند حسابداری» column of `DataTable` still needs at least one row to be detected.
- Purchase review («مرور خرید», زنجیره تامین › گزارش, `/purchase-review`): clone of the sales review (`pages/PurchaseReview.tsx`, `routes/purchaseReview.ts`, `services/purchaseReviewService.ts`, cache `lib/purchaseReviewCache.ts`) with tabs نوع خرید, تامین‌کننده, گروه کالا (per level), گروه حسابداری, کالا, اسناد, گردش (no sales-center equivalent). Purchases = lines of APPROVED `PurchaseInvoice`s (base-currency `baseAmount/baseDiscount/vatAmount`); returns = `SUPPLIER_RETURN` inventory lines (quantity; amount from `getLineAmounts`, no discount/VAT, purchase type shown as «نامشخص»); service purchase invoices are not included. - Reporting-period code (`routes/reportingPeriods.ts`): the code is **optional** — when omitted/blank on create, the system assigns `max numeric code in that fiscal year + 1` (non-numeric codes ignored; unique `(fiscalPeriodId, code)` is the race guard with a retry loop); a typed code is kept (Persian digits normalized, duplicates rejected). On edit an empty code keeps the existing one.
- Fiscal-period chain (`routes/fiscalPeriods.ts`, `pages/FiscalPeriods.tsx`): a new period's start date is forced server-side to be exactly the day after the latest period's end (no gap/overlap); create and the last period's end-date edit run in one transaction under a Postgres advisory lock (`FISCAL_CHAIN_LOCK_KEY`) so concurrent requests can't break the sequence. The new-period form auto-fills and locks the start date (editable only for the very first period) and defaults the end date to one day before the same Jalali date next year (leap years give 12/30); the end date stays editable.
- Journal-entry renumbering (single source of truth: `services/journalEntryRenumberService.ts` → `renumberJournalEntries(fiscalPeriodId, tx?)`): all DRAFT/REVIEW entries of the period are re-numbered contiguously (`number` only) starting after the highest APPROVED number, ordered by date → dailyNumber → id (two raw-SQL steps under a Postgres advisory lock; temporary negative numbers avoid the `(fiscalPeriodId, number)` unique clash). `referenceNumber`/`dailyNumber` and approved entries are never touched. Two callers, no duplicated logic: the «شماره‌گذاری مجدد» item of the journal-entries list «عملیات» menu (`POST /journal-entries/renumber`, permission `accounting.operations.journal-entries.renumber`; DataTable bulk action with `noSelection: true` = always enabled, no row selection needed) and document confirmation (`POST /document-confirmation/confirm` runs renumber + approve in ONE transaction; the page asks «اسناد تا این تاریخ شماره‌گذاری مجدد خواهند شد» before confirming). Any future caller must use the service, never re-implement it.

By explicit user decision the year-level `InventoryAccountingClose` is NOT required for confirming (the system opening document simply stays `REGISTERED`/amount-less until the accounting close finalizes it). **Stock is cumulative across fiscal years everywhere** (`computeStockAsOf`, `getMovements`, the pricing engine/validation), so the system opening doc is deliberately *neutral*: every cumulative consumer excludes it via `CARRY_FORWARD_OPENING_WHERE` (the pricing engine only includes it as the valued *anchor* once the inventory accounting close exists — see the next entry) (`warehouseStockService.ts`; `computeStockAsOf` uses `creationType: MANUAL` on the INITIAL_INVENTORY rule) — it is a carry-forward record, not a second source of stock (its serial/batch/location lines are descriptive only, see below); any new cumulative stock/movement/pricing query must apply the same exclusion or the previous year's balance is counted twice. **Opening-document detail** (`services/warehouseOpeningDetailService.ts#buildOpeningLineSpecs`): lines are built **per (goods, physical location)** with the batches/serials of that location (`InventoryLineBatch`/`InventoryLineSerial`, `physicalLocationId`) — purely *descriptive*, like a manual opening document: location is used only for `isLocationTracked` items; batch items = balance per (location, batch); serial items = serials whose net signed count is 1, at the location of their latest inbound line; serial `status/step` are NOT touched (no lifecycle run, `serialStep` = the serial's current step). Same sign rules/doc types as `computeStockAsOf`. If the detail doesn't match the per-goods balance (negative location/batch balance, stock without batch, serial count ≠ balance) the quantity close is **rejected** listing the items (nothing created). The document is excluded from every cumulative sum, including `batchService.computeBatchAvailableQuantity`. **Reopen («باز کردن», permission action `warehousing-quantity-close.reopen`, `POST /warehouse-quantity-close/:warehouseId/reopen`, `reopenWarehouseQuantity`)**: deletes the warehouse's `WarehouseQuantityClose` row and its system opening document so it can be closed again (and the confirmation revert, blocked by `assertNotQuantityClosedAfter`, becomes possible). Allowed only when (1) the warehouse is NOT confirmed in the next fiscal year (`confirmedDate < next.fromDate`) and (2) the same year's `InventoryAccountingClose` does not exist (reverse it first); also the opening document must still be untouched (REGISTERED, no amounts). One transaction, lock order = accounting close's (exclusive opening-year advisory lock → warehouse row lock), so a concurrent accounting close/reopen yields exactly one winner (tested). The status rows carry `canReopen`/`reopenBlockedReason` for the page's «باز کردن» button. The existing initial-inventory form already treats `SYSTEM` documents as read-only. Verified with a container-run script (rules, atomic rollback, audit fields, review-report neutrality, 6 parallel closes → exactly one, close-vs-revert races in both orderings).
- Inventory accounting close («بستن حسابداری موجودی» / «برگشت بستن», warehouse › «عملیات پایان دوره», `/warehousing/accounting-close`, `routes/inventoryAccountingClose.ts`, `services/inventoryAccountingCloseService.ts` + `services/inventoryAccountingGuards.ts`, `pages/InventoryAccountingClose.tsx`, models `InventoryAccountingClose` [unique per fiscal period; `closedAt/closedById`, `nextFiscalPeriodId`, `openingDate`] + `InventoryAccountingCloseLog` [CLOSE/REVERSE audit], permission form `warehousing-accounting-close`: `view`/`close`/`reverse`): whole current fiscal year, all eligible warehouses (same `implementationDate ≤ period end` rule as the quantity close) **in one transaction**. Preconditions re-read inside the tx: exclusive advisory lock on the *next* fiscal period (`lockOpeningYearExclusive`, key 7100004), then `SELECT … FOR UPDATE` on every eligible warehouse row (same lock as confirm/revert/quantity-close), then every eligible warehouse must have a `WarehouseQuantityClose` for the period and still be confirmed through year end (otherwise a clear error naming the warehouses). It does NOT create documents: for each existing system opening line (from `WarehouseQuantityClose.openingDocumentId`) it writes one `DocumentItemAmount` of the new `priceType=ACCOUNTING_CLOSING` = the year-end value from `computeItemKardex` (the single kardex implementation extracted from `priceItem`) computed **per item across all warehouses** over the whole fiscal-year window, then allocated to that item's per-warehouse opening lines **proportionally to their quantities** (`allocateByQuantity`: each share rounded to the base-currency decimals, the rounding remainder added to the largest-quantity line so the shares sum exactly to the item total; the pooled kardex quantity must equal the sum of the opening lines, value ≥ 0, and any user-priced document without an amount blocks the close). **The close also confirms the opening documents**: after writing the amounts it sets every next-year system opening document to `FINALIZED` (+`finalizedAt`) — like «تایید حسابداری» of a manual opening, so the initial-inventory form/list show the amounts (they are hidden for `REGISTERED` documents). The bulk warehouse confirmation/revert (`finalizeWarehouseDocumentsUpTo`/`revertFinalizedWarehouseDocumentsAfter`) deliberately skip `CARRY_FORWARD_OPENING_WHERE` documents: only the accounting close (and its reversal) finalizes/un-finalizes them. Reversal (`reverseInventoryAccountingClose`) takes the same exclusive lock, refuses when any `GoodsPricingStatus` exists for a reporting period of the next fiscal year (irreversible) or when the next year's own close exists — **it does NOT depend on warehouse confirmations in the next year** (explicit user decision: a warehouse confirmed in the new year keeps its confirmation; the reversal just sets the opening documents back to `REGISTERED`), then deletes exactly the `ACCOUNTING_CLOSING` rows, sets the opening documents back to `REGISTERED`, and deletes the close row (log row stays). **Pricing integration / item-level valuation** (`goodsPricingService.ts`, `goodsPricingValidation.ts`, `routes/goodsPricing.ts`): valuation is **item-level only** — one pooled moving-average kardex per item across ALL warehouses (warehouse is not part of the key and plays no role; transfers are net-zero in the pool; the warehouse stays on the document lines). `computeItemKardex(itemId, {windowFrom, periodFrom, toDate})` loads the window **fiscal-year start … reporting-period end** (`pricingDocumentWhere`; later movements have no effect; opening inventory — manual, or the valued system opening dated the year start — is a valid record; other years' system openings are excluded) but only lines dated inside the reporting period are valued/written: earlier lines of the same year enter the pool with their **stored** amounts and are never rewritten (no new `ENGINE_CORRECTION`; supplier returns of pre-period receipts get the proportional share of the receipt's stored amount). The first movement date per item (`firstMovementDate`, across warehouses, opening included) drives `findPreviousValuationProblems`: an item with any movement before the period start (within the year window, **the opening inventory counts as a movement**) is *subject*; for it the latest earlier reporting period **of the same fiscal year** in which it had any movement must have a `GoodsPricingStatus` for the item — a status means "processed", even without new movement — otherwise validation/`priceItem` fail. An opening-only item is therefore subject too (its opening falls in the first period, which must have been processed for it — it is listed and recorded there); only items first moved in the current period are not blocked. Each processed item gets a status row even when it has no lines in the period, and the candidate listing includes opening-only items so later periods can recognize them. There is NO check on the previous *fiscal year* at item level; the only year-level rule is `getPreviousYearAccountingCloseProblem` (previous fiscal year must be accounting-closed; none = no check). `priceItem` is ONE transaction that first takes the **shared** advisory lock for its fiscal year (a concurrent reversal is serialized: pricing first ⇒ reversal rejected, reversal first ⇒ pricing rejected) and re-checks both rules inside. Stock *quantities* stay cumulative and still ignore the system openings (`CARRY_FORWARD_OPENING_WHERE`). **Closed-year price lock** (`inventoryAccountingGuards.ts#assertFiscalYearNotAccountingClosed` / `assertLineAmountChangeAllowed`): once a fiscal year has an `InventoryAccountingClose`, NO price change is allowed in it — `priceItem` and `revertItem` of its reporting periods, and (centrally, inside `documentItemAmountService.setLineAmount` / `deleteLatestLineAmount`, so every caller — purchase-invoice approve/unapprove CROSS_ENTITY, service-invoice INBOUND_RELATED_COST, manual opening/adjustment/production amounts — is covered) any amount write/delete on a line whose document belongs to that year (the `ACCOUNTING_CLOSING` write of the close itself is exempt). The only way out is «برگشت بستن». The guard takes the **shared** advisory lock of the next year (the same key close/reverse take exclusively) before reading, so an in-flight amount change finishes before a close reads the data, and a change started after the close is rejected (tested with a held transaction racing the close); the not-closed result is cached per transaction. **Year-valuation precondition for the close** (`getYearEndValuationProblem`, checked inside the close transaction and shown as `closeBlockedReason`): every item with any movement in the fiscal year window (opening included) must have a `GoodsPricingStatus` in the **last reporting period** of the year (the chain rule makes that imply all earlier periods), the year must have a reporting period, and the last reporting period must reach the year end if movements follow it — because after the close nothing in the year can be priced any more.

## Versioning & releases

- The system has one release version (semver `major.minor.patch`), first set to **1.0.0**. It lives in four files that must always match — `backend/package.json` (the source of truth the API reads), `backend/package-lock.json`, `frontend/package.json`, `frontend/package-lock.json` — and is changed **only** by `node scripts/release.mjs patch|minor|major|x.y.z` (never edit those fields by hand). `node scripts/release.mjs --check` verifies the four files agree and that `CHANGELOG.md` has the current version (run it before tagging/building).
- Choosing the number: **patch** = bug fixes only; **minor** = new backward-compatible features (including additive migrations); **major** = breaking change or a manual migration step for the operator.
- Every change that matters to users/operators is written under `## [Unreleased]` in `CHANGELOG.md` **in the same PR that makes it**. A release = the script (it names the Unreleased section with the version and date, opens a fresh empty one, and refuses to run when Unreleased is empty) → `git commit -m "Release vX.Y.Z"` → `git tag vX.Y.Z` → build the Docker images tagged with the version (`…/accounting-erp-backend:X.Y.Z` and `:latest`, same for frontend).
- **Delivery images are compiled** (`backend/Dockerfile.release`, `frontend/Dockerfile.release`, built only by `node scripts/build-release.mjs [--out E:\backups]`; the plain `Dockerfile`s + `docker-compose.yml` stay the dev setup with source bind-mounted and tsx/Vite): backend = `tsc -p tsconfig.release.json` (rootDir `.`, includes `prisma/seed.ts`) → `release/compile-bytecode.cjs` turns every `.js` into V8 bytecode `.jsc` with **bytenode** (same tree, so `require('./x')` resolves `x.jsc` and circular imports behave as before; run as `node -r bytenode dist/src/index.jsc`; `package.json` and `src/assets` are copied into `dist` because `about.ts`/`printService.ts` read `__dirname/../..`), runtime image has prod deps only (+ `prisma` CLI for `migrate deploy`, now a dependency) and no `src`/`tsx`/`typescript`/`.ts`/`.map`. Both stages use the same `node:20-alpine` build (bytecode is V8-version-bound) and **no V8 flags may be added to the run command**. Source maps are NOT in the image: `build-release.mjs` extracts them to `<out>\sourcemaps-<version>` (keep them to read production stack traces). frontend = `npm run build` → `nginx:1.27-alpine` on port 5173 (SPA fallback, hashed assets cached, `config.js`/`index.html` no-store); `public/config.js` (dev: empty) is overwritten at container start by `release/40-erp-config.sh` from env `VITE_API_URL`, read by `lib/apiUrl.ts` (the single `API_URL`; api.ts/Management/ManagementBackup import it). tar contains both `:<version>` and `:latest` tags. Limit: bytecode raises the cost of reading/patching but is not unbreakable for someone with root and V8 reverse-engineering skills (the licence public key is still a constant inside the bytecode); the contract is the other half. Maintenance scripts run as `node -r bytenode dist/src/scripts/<name>.jsc`.
- The About dialog (top bar, next to user settings; `components/AboutModal.tsx`, `routes/about.ts`, `GET /api/about`) shows «نسخه» (the release version), «پایگاه داده» = the **name of the connected database** (`current_database()`, with the PostgreSQL version) and «نسخه‌ی پایگاه داده» = the **schema version**: the newest Prisma migration applied on that database (`_prisma_migrations`, its 14-digit timestamp + name) with the number of applied migrations. It warns when the newest migration bundled with the running app is not yet applied (`database.upToDate === false`) and when the frontend's own version (`__APP_VERSION__`, injected from `frontend/package.json` by `vite.config.ts`) differs from the server's.

## Working rules for this repo

- Match existing patterns: new route file + register in `index.ts` + `authz/registry.ts` + `navConfig.ts` + `App.tsx` + page; schema change ⇒ Prisma migration.
- Reuse `journalEntryService`, `assertRecordNotStale`, fiscal scoping, and shared components instead of re-implementing.
- Don't commit `dist/`, `~$` temp files, or `.env`.
- User-visible changes get a line under `## [Unreleased]` in `CHANGELOG.md` in the same PR; versions are bumped only with `scripts/release.mjs` (see «Versioning & releases»).
